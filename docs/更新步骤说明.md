# 在线更新（Updater）配置与排错

CodeShelf 使用 Tauri updater 插件 + GitHub Releases 实现应用内在线更新。

本文只讲**更新机制本身**：签名密钥、GitHub Secrets、CI 行为与常见问题。
日常发版命令见 [开发规范 · 发版](CONVENTIONS.md#发版)，构建与打包见 [BUILD.md](../BUILD.md)。

> **Updater 签名与 macOS 代码签名不是一回事。** Updater 私钥只用于验证更新包未被
> 篡改，不会让 macOS 信任 DMG 或 `.app`。浏览器下载后的首次安装还受 Gatekeeper、
> Developer ID 与 notarization（公证）约束。

> 下面第一、二节是**一次性配置**，配好后不用再动。日常发版只需第四节的一条命令。

---

## 一、生成签名密钥（一次性）

Tauri updater 要求对更新包签名，防止被篡改。

```bash
npm run tauri signer generate -- -w ~/.tauri/codeshelf.key
```
执行后会输出：

```
Please enter a password to protect the secret key:    # 输入密码（可留空直接回车）
Password:
Deriving a key from the password and target...

Your keypair was generated successfully
Private: /Users/you/.tauri/codeshelf.key
Public:  dW50cnVzdGVkIGNvbW1lbnQ6IG1pbmlzaWduIHB1Y...   ← 复制这个公钥
```

输出的 **公钥** 填到 `src-tauri/tauri.conf.json`：

```json
"plugins": {
  "updater": {
    "pubkey": "这里粘贴公钥",
    "endpoints": [
      "https://github.com/en-o/codeshelf/releases/latest/download/latest.json"
    ]
  }
}
```

**私钥 `~/.tauri/codeshelf.key` 必须妥善保管**，下一步要用，且丢失后老版本无法再收到更新。

## 二、配置 GitHub Secrets（一次性）

仓库 **Settings → Secrets and variables → Actions → New repository secret**：

| Secret | 值 |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | `~/.tauri/codeshelf.key` 的**全部内容** |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 生成密钥时设的密码（没设就留空） |

## 三、macOS 代码签名与公证

`src-tauri/tauri.release.conf.json` 当前配置了 `"signingIdentity": "-"`。这是 Tauri
支持的 ad-hoc 签名兜底：即使暂时没有 Apple Developer ID，也会对整个 `.app` 及资源做
完整封印，避免只留下 Rust 链接器的主程序签名、最终被 macOS 判为“应用已损坏”。CI 会用
`codesign --verify --deep --strict` 检查应用签名，并用 `hdiutil verify` 检查 DMG。

ad-hoc 签名**不代表发布者身份，也不等于 Apple 公证**。要让公网下载的安装包通过
Gatekeeper 的完整信任链，仍需 Apple Developer Program 的 `Developer ID Application`
证书，并在 CI 中配置签名与公证凭据：

| Secret / 配置 | 用途 |
|---|---|
| `APPLE_CERTIFICATE` | `.p12` 证书的 Base64 内容 |
| `APPLE_CERTIFICATE_PASSWORD` | 导出 `.p12` 时设置的密码 |
| `APPLE_SIGNING_IDENTITY` | `Developer ID Application: ...` 签名身份 |
| `KEYCHAIN_PASSWORD` | CI 临时 keychain 密码 |
| `APPLE_ID` | 公证使用的 Apple ID |
| `APPLE_PASSWORD` | Apple ID 的 app-specific password |
| `APPLE_TEAM_ID` | Apple Developer Team ID |

接入正式证书时，应让 workflow 把上述值传给 Tauri，并用真实
`APPLE_SIGNING_IDENTITY` 覆盖 release config 中的 `-`。正式发布前除现有校验外，还要确认：

```bash
codesign --verify --deep --strict --verbose=4 CodeShelf.app
spctl --assess --type execute --verbose=4 CodeShelf.app
xcrun stapler validate CodeShelf.app
xcrun stapler validate CodeShelf_<版本>_aarch64.dmg
```

## 三点五、正式版与预览版

**两条独立基线，渠道由版本号决定，没有额外开关**：

| 版本号 | 渠道 | 基线分支 | 更新源（编译期烧进包里） | GitHub Release |
|---|---|---|---|---|
| `0.2.0` | 正式版 | `main` | `releases/latest/download/latest.json` | 正常 Release |
| `0.2.0-1` | 预览版 | `main-v` | `releases/download/preview/latest.json` | Pre-release |

两条线**各自更新、互相看不见**：正式版永远只检查到正式版，预览版只检查到预览版。
想换线只能自己去 Releases 下载对方的安装包覆盖安装（数据不丢，装完即按新版本号切换渠道）。

隔离有两道，缺一不可：

1. **编译期**：预览版构建多叠一层 `src-tauri/tauri.preview.conf.json`，把 updater
   endpoint 换成预览专属清单 —— 正式版的包里物理上就没有预览清单的 URL，反之亦然。
2. **运行期**：`services/updater` 的 `checkUpstream()` 再核对一次远端版本号的渠道，
   对不上直接当"没有更新"。清单配错或端点被顶掉时兜住。

预览版的更新端点是**固定 tag `preview`** 上的 `latest.json`（GitHub 的 `latest`
会跳过 pre-release，预览线拿不到这个入口，只能自己立一个）。它由
`.github/workflows/preview-manifest.yml` 在**人工 Publish 某个预览版之后**同步过去 ——
必须等 Publish：Draft 的附件对外不可下载，提前同步等于把用户指向一个下不动的包。

三个约束**不要改**：

- **后缀只能是纯数字**（`-1`、`-2`）。MSI 的 ProductVersion 不接受 `-beta.1`
  这类标识符，用了 Windows 出包会在 CI 上直接失败。
- **预览版必须发成 GitHub Pre-release**（CI 按版本号自动设置）。`/releases/latest`
  会跳过 pre-release，正式版用户的 updater endpoint 才不会被预览版顶掉。
- **`preview` 这个 release 自己也必须是 Pre-release**，否则它会成为仓库的 `latest`，
  正式版用户的端点直接指向预览清单。

## 四、发布新版本

```bash
./scripts/release.sh 0.2.0      # 正式版：必须在 main 上跑（Linux/macOS/WSL）
./scripts/release.sh 0.2.0-1    # 预览版：必须在 main-v 上跑
scripts\release.bat 0.2.0       # Windows，同上
```

脚本会同步 `package.json`、`tauri.conf.json`、`Cargo.toml` 三处版本号，提交并推送 `release/0.2.0` 分支，
最后切回对应的基线分支。**基线分支由版本号推出**（带 `-N` 即 `main-v`），
在错误的分支上跑会被前置校验直接拦下 —— 在 `main` 上打预览版号等于把正式版代码发成预览版。

> 发版前记得更新 `RELEASE_NOTES.md`——CI 会读它作为 Release 正文。

推送后 GitHub Actions 自动：

1. 在 Windows、macOS（x86 + ARM）、Linux 并行构建
2. 生成安装包与签名文件
3. 创建 **Draft Release**，上传全部产物（含关键的 `latest.json`）
4. 在 workflow 的 Summary 里输出草稿信息：构建 commit、Release 绑定的 commit、产物清单

最后到 GitHub **Releases** 页面找到草稿，确认无误后 **Publish release**——发布后用户才能检测到更新。

> **CI 不会自动发布。** 发布是对外且不可逆的动作（用户端立刻能检测到更新），
> 构建成功不等于可以发版 —— 还要人工核对产物、签名和 release notes。
> 这一点 workflow、发版脚本与本文档保持一致：没有人点 Publish，Release 就一直是 Draft。
>
> Summary 里会同时列出「构建 commit」和「Release 绑定 commit」，两者必须相同；
> 不同则说明 tag 落在了别的提交上，**不要发布**。

## 五、用户端更新

用户打开 **设置 → 应用更新 → 检查更新**，有新版本时显示版本号与更新日志，点击「下载并安装更新」后自动完成：下载 → 验证签名 → 安装 → 重启。

预览版流程完全一样，只是检查到的永远是新的**预览版**；设置页会显示「预览版」角标并说明这一点。
跨渠道切换不在应用内提供入口 —— 更新功能里看不到对方渠道的任何信息。

## 六、相关文件

```
.github/workflows/release.yml           # 构建发布工作流
.github/workflows/preview-manifest.yml  # 预览版 Publish 后同步 preview 端点
scripts/release.sh / release.bat  # 发版脚本（版本号同步 + 推分支）
scripts/release-precheck.mjs      # 前置校验 + 基线分支判定（两平台共用）
src-tauri/tauri.conf.json         # updater 配置（pubkey、正式版 endpoint）
src-tauri/tauri.preview.conf.json # 预览版构建叠加：换成预览专属 endpoint
src-tauri/src/lib.rs              # 注册 updater 插件
src/services/updater/index.ts     # 更新检查与下载逻辑
src/pages/Settings/               # 更新设置界面
RELEASE_NOTES.md                  # CI 读取作为 Release 正文
```

## 七、常见问题

**构建失败提示缺少 `TAURI_SIGNING_PRIVATE_KEY`**
→ 检查第二节的两个 Secret 是否都已添加。

**macOS 应该下载哪个文件**
→ Apple Silicon（M1 / M2 / M3 / M4 等）下载 `_aarch64.dmg`，Intel Mac 下载
`_x64.dmg`。`.AppImage` 只供 Linux 使用，macOS 不支持。

**macOS 提示“CodeShelf 已损坏”**
→ 先确认使用了匹配处理器的 DMG。若是 v0.1.44，已确认该版本只有主 Mach-O 的 linker
签名，完整 bundle 校验失败且没有公证票据；这是发布包问题，不是换成 AppImage 能解决的。
请使用修复后的版本。正式 Developer ID 与公证尚未接入前，ad-hoc 签名版本仍可能显示
“无法验证开发者”，需在 Finder 中右键应用并选择“打开”。

**用户检查更新提示网络错误**
→ 确认 Release 已从 Draft 改为 **Published**；确认 Assets 中包含 `latest.json`；国内网络可能需要代理或改用镜像 endpoint。

**更新后版本没变**
→ 三处版本号必须一致且大于当前版本：`tauri.conf.json`、`package.json`、`Cargo.toml`。用发版脚本可避免漏改。

**推送到 main 会触发构建吗**
→ 不会。只有 `release/*` 分支触发。

**如何手动触发构建**
→ 工作流已配 `workflow_dispatch`：Actions → Release → Run workflow，**选择要构建的 release 分支**。
不需要（也无法）填版本号 —— 版本的唯一真相源是分支里的 manifest，由 `scripts/release.sh` 写入。
workflow 启动时会校验 `tauri.conf.json` / `package.json` / `package-lock.json` / `Cargo.toml`
四处版本号完全一致，不一致直接失败。

**只想构建 Windows**
→ 改 `.github/workflows/release.yml` 的 `matrix`，只保留 `windows-latest`。
