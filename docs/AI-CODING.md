# AI Coding 实践（SDD）

> 本项目大量代码由 AI 协作产出。这份文档说明**怎么协作才不会失控**。
> 硬约束清单在根目录 [CLAUDE.md](../CLAUDE.md)（AI 每次会话自动加载），本文是给人读的方法论与流程。

## 为什么需要方法论

AI 写代码有三个绕不开的固有特性——不是模型不够强，换个模型也一样：

| 瓶颈 | 表现 | 在本项目的真实例子 |
|---|---|---|
| **概率性输出** | 同样的提示，两次结果可能不同 | 同一个「自定义终端」需求，两次实现走了完全不同的分支结构 |
| **上下文限制** | 多轮对话后"遗忘"早期约定 | 前面说过"sidecar 依赖不能删"，几十轮后依然差点删掉 `deepagents` |
| **局部视野** | 只看得到给它的那部分代码 | 只改 `launch.rs` 的启动路径，漏掉 `system.rs` 里同源的另一份拷贝 |

**核心做法：把约束写下来，让它成为唯一真相源。** 对 AI 来说，没写下来的规则就是不存在的规则——这正是 [CLAUDE.md](../CLAUDE.md) 存在的意义。

## 四步流程

标准 SDD 流程 **Specify → Plan → Implement → Validate**，但本项目按需裁剪，不搞形式主义。

### Specify（定义要做什么）

- 说清 **目标** 和 **Non-Goals**。不写"不做什么"，AI 一定会自由发挥。
- 提供**参考代码入口**，缩小搜索空间。别让 AI 在整个仓库大海捞针——直接告诉它"这个功能参考 `toolbox/ssh_tunnel/`"。
- 显式补充约束：涉及 Windows？涉及数据文件读写？涉及 Tauri 命令签名？把 [CLAUDE.md](../CLAUDE.md) 里对应条目点出来。

### Plan（怎么做）

- 让 AI **带着具体问题**读代码："现有的隧道模块怎么管理生命周期？扩展点在哪？"——而不是泛泛的"了解一下项目"。
- 要求它**主动提出疑问和风险**：需求有没有遗漏？和现有架构有没有冲突？把问题暴露在方案阶段，而不是编码后。
- 方案要审**架构合理性**，不只是"能不能跑"。AI 给的方案常常能跑但引入了不必要的复杂度。

### Implement（写）

**先搭框架，再填细节。** 先产出目录结构、接口定义、类型——"能编译但没实现"的骨架。框架必须先确认，因为后面所有代码都长在它上面，改框架的成本远高于改实现。

然后按模块逐个实现，**一次一件事**。上下文越聚焦，产出质量越高。

### Validate（验证）

**验证不是最后一步，是每一步都要做的事。**

- 每步产出与输入对齐（代码是否真的实现了方案说的东西）
- 跑 [CLAUDE.md](../CLAUDE.md#验证命令) 的验证命令
- **涉及 Windows 专有代码，必须 Docker 交叉编译**——这是本项目最容易漏的一环，macOS 上 `cargo check` 全绿也可能是错的
- 复杂改动可用**多模型交叉评审**，利用模型间的认知差异发现盲点

> 评审的重点不是"逻辑对不对"——逻辑层面 AI 很少犯错。重点是**"设计好不好"**：有没有过度抽象？错误处理是不是在吞异常？边界条件够不够健壮？跨模块风格是否一致？

## 什么时候写 Spec

**Spec 会膨胀，膨胀的 Spec 反而是负担。** 本项目的门槛：

| 需要写 Spec | 不需要 |
|---|---|
| 新增工具箱工具 | 日常 bugfix |
| 跨模块重构 | UI 微调、文案修改 |
| 数据结构/存储迁移 | 单文件内的局部优化 |
| 外部协议变更（MCP、sidecar RPC） | 依赖升级 |

写的话放 `docs/specs/`，模板见 [specs/README.md](specs/README.md)。

**自检**：如果"换一个技术栈来实现，这份 Spec 是否依然有效？"答案是否——说明你把 HOW（实现细节、伪代码）混进了本该只写 WHAT 的 Spec 里，需要抽象度上提。

## 上下文工程

比"怎么写提示词"重要得多的是"给什么上下文"。原则是**恰好足够**：

- **不能多**：上下文过长，关键约束会淹没在中间（Lost in the Middle）
- **不能少**：信息不足时 AI 会自信地"脑补"，给出看似合理实则错误的答案

实践技巧：

- **渐进披露**：实现模块 A 时只加载 A 的相关代码和它直接依赖的接口。需要全局视角时加载架构概览，而不是所有模块的细节。
- **一次对话一个主题**：话题混杂会互相污染。做完一个主题就开新会话。
- **先让 AI 复述**：让它先说"我理解的需求是什么、准备改哪些文件"，比直接让它写代码更容易早期发现偏差。

## 记忆与知识沉淀

本项目**不引入额外的记忆工具**——对个人项目来说，下面三样已经够用，且天然随 Git 版本化：

| 载体 | 存什么 |
|---|---|
| [CLAUDE.md](../CLAUDE.md) | 长期硬约束（踩过的坑固化成规则） |
| `docs/specs/` | 大功能的背景与决策 |
| Git 提交历史 | 变更的来龙去脉（所以[提交信息要写清楚](CONVENTIONS.md#提交信息)） |

**关键习惯：踩了坑就往 CLAUDE.md 加一条。** 一个坑踩两次，就是约束层没尽到责任。CLAUDE.md 现有的 8 条硬约束全部是这样积累出来的。

## 质量责任

AI 提升了代码产出效率，但**质量责任没有转移**——它依然在人身上。

- 不能因为"AI 写的应该没问题"就放松评审
- 自动化检查（tsc / cargo check / 测试）是底线，不是充分条件
- 涉及数据安全（存储写入）、平台专有代码（Windows）、外部协议（MCP）的改动，必须人工确认
