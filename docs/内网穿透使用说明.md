# 内网穿透（公网映射）使用说明

> 工具箱 → 内网穿透。把本地开发服务临时映射到你自己 VPS 的公网端口，
> 用于**微信/支付回调**等只能填外网域名/IP、本地收不到的调试场景。

## 一、它是什么 / 不是什么

- **原理**：SSH 反向隧道（等价 `ssh -N -R 绑定:公网端口:本地主机:本地端口 用户@VPS`）。
  你的 VPS 在某个端口监听，收到的公网请求经 SSH 加密通道回流到你本机的服务。
- **需要你自己的 VPS**：一台有公网 IP（最好还有域名）、能 SSH 登录的服务器。
  微信服务器的回调是"入站请求"，必须有一个公网可路由的稳定入口——这就是你的 VPS。
- **不是**无服务器的魔法 P2P；也**不是**现有「SSH 隧道」工具（那个是正向 `-L`，
  把远程端口拉到本地；本工具方向相反，把本地推到公网）。

## 二、前置准备（VPS 侧，一次性）

1. **能 SSH 登录**：私钥 / 密码 / 或 `~/.ssh/config` 里配好的 Host 别名，任选其一。
2. **（仅当要对公网开放时）开启 GatewayPorts**：编辑 VPS 的 `/etc/ssh/sshd_config`
   （较新的 Ubuntu/Debian 可能在 `/etc/ssh/sshd_config.d/*.conf`），加上（推荐 `clientspecified`）：
   ```
   GatewayPorts clientspecified
   ```
   然后 `sudo systemctl restart sshd`（Ubuntu/Debian 可能叫 `ssh`；重启不会断开当前 SSH 连接）。
   - `no`（默认）只绑 `127.0.0.1`，公网连不上；`yes` 绑所有网卡；`clientspecified` 听本工具的
     （不勾"对公网开放"就只绑本机，勾了才对外），最精准安全。
   - 验证：`sudo sshd -T | grep gatewayports`。
   - 配置文件里**本来没有 `GatewayPorts` 也正常**，即默认关闭状态。
3. **放行端口**：云厂商安全组 / 防火墙放行你要用的公网端口（如 9000）。
4. **（推荐）用 nginx 反代 + HTTPS + 域名**：见下方「推荐姿势」。

## 三、字段说明

新建映射时表单分三段：

| 段 | 字段 | 说明 |
|----|------|------|
| **本地服务** | 本地主机 / 本地端口 | 要暴露的本地服务，通常 `127.0.0.1:你的端口` |
| **SSH 服务器（VPS）** | 主机 / 端口 / 用户 / 认证 | 公网入口，需可 SSH 登录 |
| **公网映射** | 公网端口 | VPS 上对外暴露的端口 |
| | 域名（可选） | 仅用于生成展示的公网地址，不影响转发 |
| | **对公网开放（0.0.0.0）** | 勾选=绑 `0.0.0.0`（整个互联网可达，需 GatewayPorts）；不勾=绑 `127.0.0.1`（仅 VPS 本机可达，配 nginx 反代） |
| | 断线自动重连 | 网络切换 / 休眠恢复后自动重建 |

生成的**公网地址**（列表里可一键复制）= `http://{域名或SSH主机}:{公网端口}`，
这就是你填到微信后台回调 URL 的地址。

## 四、快速测试（5 分钟验证链路）

1. 本机起一个测试服务：
   ```bash
   python3 -m http.server 8000
   ```
2. 新建映射：
   - 本地服务：`127.0.0.1` / `8000`
   - SSH 服务器：你的 VPS 主机 / 22 / 用户 / 私钥
   - 公网映射：公网端口 `9000`，先**不勾**「对公网开放」（仅本机测试）
3. 点「启动」，状态变绿「运行中」。
4. 到 VPS 上验证（仅本机绑定时用 VPS 自己访问）：
   ```bash
   curl http://127.0.0.1:9000/
   ```
   能看到 `python -m http.server` 的目录列表 = 链路通。列表里的「连接 / ↓↑流量」会增长。
5. 若要**外网直接访问**：勾选「对公网开放」重新保存并启动（VPS 需已 `GatewayPorts yes`），
   然后在任意外网机器：
   ```bash
   curl http://你的域名或VPS_IP:9000/
   ```

## 五、对接微信回调（典型用法）

1. 本地起你的回调服务（如 `http://127.0.0.1:8080`）。
2. 新建映射把 `127.0.0.1:8080` 映射到 VPS 公网端口（推荐配合 nginx 走 80/443，见下）。
3. 复制生成的公网地址，填到微信公众平台 / 商户后台的「回调 URL」。
4. 触发回调，观察本地服务是否收到请求。用完**及时点停止**。

## 六、推荐姿势：nginx 反代 + HTTPS + 域名（更安全）

微信回调通常要求 HTTPS。做法：映射时**不勾**「对公网开放」（只绑 `127.0.0.1:9000`），
由 VPS 上的 nginx 对外提供 443 + 证书，反代到 `127.0.0.1:9000`：

```nginx
server {
    listen 443 ssl;
    server_name dev.example.com;
    ssl_certificate     /etc/letsencrypt/live/dev.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dev.example.com/privkey.pem;

    location /wechat/callback {          # 只暴露具体回调路径，减小攻击面
        proxy_pass http://127.0.0.1:9000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

这样公网只暴露 `https://dev.example.com/wechat/callback`，隧道本身不直接对公网开放，最安全。

## 七、安全须知（务必阅读）

- **本地服务自身没有鉴权**：一旦对公网开放，任何人都能访问被映射的服务。仅用于临时调试，
  用完立刻停止；生产切勿长期挂着。
- **优先只绑 `127.0.0.1` + nginx 反代**，只暴露需要的路径，而不是直接 `0.0.0.0` 全暴露。
- **凭据存储**：私钥 passphrase、SSH 密码在本机明文保存；首版**未做 known_hosts 校验**
  （接受任意主机公钥），请只连自己可信的 VPS。
- **端口冲突**：VPS 公网端口若已被占用，启动会报错（提示见「最近错误」）。

## 八、如何关闭

**1）临时关（最常用）**：在工具里点**停止**，VPS 上那个端口立刻不再监听。日常调试完这样就够了，跟改不改服务端配置无关。

**2）彻底收回服务端能力**（把 `GatewayPorts` 改回默认关闭）：

```bash
# 先看当前到底是什么值（不管配置文件里有没有那行）
sudo sshd -T | grep gatewayports
#  no             -> 已经是关闭状态，无需操作
#  clientspecified / yes -> 是开着的，按下面关

# 找到之前加的那行（可能在主文件，也可能在 drop-in 目录）
sudo grep -ri gatewayports /etc/ssh/sshd_config /etc/ssh/sshd_config.d/

# 编辑对应文件，把 GatewayPorts 那行删掉，或改成 no：
sudo vim /etc/ssh/sshd_config      # 若在 drop-in，则编辑 /etc/ssh/sshd_config.d/xxx.conf
GatewayPorts no

# 重启 sshd 使其生效（不会断开你当前的 SSH 连接）
sudo systemctl restart sshd        # Ubuntu/Debian 可能叫 ssh: sudo systemctl restart ssh

# 再次确认已关闭
sudo sshd -T | grep gatewayports   # 应输出 gatewayports no
```

> 删掉那行和写 `no` 效果一样（默认就是 `no`）；配置文件里本来没有 `GatewayPorts` 也属正常，即处于关闭状态。

**3）云端**：删掉云安全组里为该端口开的入方向规则（阿里云 / 腾讯云控制台，入方向规则里删除）。

## 九、故障排查

| 现象 | 可能原因 / 处理 |
|------|----------------|
| 启动即报「请求远端端口转发失败」 | VPS 该端口被占用；或对公网开放但未 `GatewayPorts yes`；换端口或改配置 |
| 状态一直「重连中」 | SSH 连不上：核对主机/端口/用户/私钥；VPS 防火墙是否放行 22 |
| VPS 本机 curl 通、外网不通 | 未开 `GatewayPorts yes`，或云安全组没放行公网端口 |
| 外网访问 502/连接拒绝 | 本地服务没起，或本地主机/端口填错；隧道只是转发，本地得真的在监听 |
| 频繁断开 | 网络不稳；保持「断线自动重连」开启，会指数退避自动重建 |

## 十、与「SSH 隧道」工具的区别

| | SSH 隧道（`-L` 正向） | 内网穿透（`-R` 反向，本工具） |
|--|--------------------|------------------------------|
| 方向 | 远程端口 → 本地 | 本地服务 → 公网 |
| 典型场景 | 连远程 Redis/MySQL/管理面板 | 微信回调、外网访问本地开发服务 |
| 监听在 | 本机 | 你的 VPS |

两者互相独立，互不影响。

## 十一、实现原理（含 Java 复现思路）

### 1. 一句话原理

用的是 **SSH 反向端口转发**（remote forwarding，即 `ssh -R`）。本机主动连上 VPS 的 SSH
服务，让 VPS **替你在公网端口上监听**；有人连那个端口时，SSH 服务端把这条连接"塞进"
已经建立好的 SSH 加密通道推回本机，本机再把它转发给本地服务。

### 2. 为什么能穿透 NAT / 无需公网 IP

关键在**连接方向**：本机 → VPS 是**出站**连接，而出站连接 NAT / 防火墙默认都放行。
一旦这条 SSH 长连接建好，双方都能在它上面开"逻辑通道"，于是服务端就能借这条已有连接
把**入站**流量推给本机。所以本机全程：不监听任何公网端口、不需要公网 IP、不用在路由器
上做端口映射。公网入口完全由 VPS 承担——这也是花生壳 / frp / ngrok 的同一套内核思路。

### 3. 协议层怎么做到的（SSH Connection Protocol，RFC 4254）

一条 SSH 传输连接上可以复用很多"通道(channel)"。反向转发主要用两步：

- **a) 申请监听**：认证成功后，客户端发一个**全局请求** `SSH_MSG_GLOBAL_REQUEST`，
  请求名 `"tcpip-forward"`，带上"要在服务端绑定的地址 + 端口"（如 `0.0.0.0:9000`）。
  服务端据此 `bind() + listen()` 那个端口并回成功应答（端口填 0 时应答里会给实际分配的端口）。
  绑定地址允不允许 `0.0.0.0` 由服务端 `GatewayPorts` 决定（见第 6 点）。
- **b) 转发每个入站连接**：外部每打到 9000 一次，服务端 `accept()` 后**不自己处理**，
  而是在 SSH 连接上向客户端发 `SSH_MSG_CHANNEL_OPEN`，通道类型 `"forwarded-tcpip"`，
  附带被连地址/端口 + 来源地址/端口。客户端收到后：① 向本地目标 `127.0.0.1:8080`
  发起一个普通 TCP 连接；② 确认打开该通道；③ 之后把「SSH 通道 ↔ 本地 TCP」两个方向的
  字节流互相搬运（`SSH_MSG_CHANNEL_DATA`），直到任一端 EOF/关闭。

消息时序（一次外网请求）：

```
本机(客户端)                     VPS(sshd)                    外网(微信)
   │──── TCP 连接 + SSH 认证 ─────▶│
   │──── GLOBAL_REQUEST           │
   │     "tcpip-forward" :9000 ───▶│  bind()+listen() 9000
   │◀──── 成功应答 ────────────────│
   │                              │◀──────── 连接 :9000 ───────│
   │◀──── CHANNEL_OPEN            │  accept()
   │      "forwarded-tcpip" ──────│
   │  连 127.0.0.1:8080           │
   │──── OPEN_CONFIRMATION ──────▶│
   │◀════ CHANNEL_DATA 双向搬运 ═══▶│◀═══ 请求/响应字节流 ══════▶│
```

- **多路复用**：外部每来一个连接就开一个新的 `forwarded-tcpip` 通道，全部跑在同一条 SSH
  连接上，互不干扰。
- **流量控制**：每个通道有"窗口(window)"，接收方按可用窗口通告能收多少，发送方据此节流，
  避免快的一端压垮慢的一端。
- **保活 / 重连**：SSH 层用 keepalive（如每 10s）探测死连；连接断了，客户端必须**重新连接
  并重新发 `tcpip-forward`**——这一步很关键，重连后不重新申请监听，端口不会自动恢复。

> 本工具就是用 Rust 的 `russh` 库这么实现的：认证后调 `tcpip_forward` 发全局请求；
> 实现 `forwarded-tcpip` 通道回调，在里面拨本地端口 + 双向对拷；断线指数退避重连并
> 重新 `tcpip_forward`。

### 4. 用 Java 复现的两条路线

**路线 A：直接用现成 SSH 库（推荐，几步就通）**

Java 生态里 JSch、Apache MINA SSHD、sshj 都支持反向转发，第 3 点的 a~b 已被库封装好，
你只需：

1. **建立会话并认证**：连 VPS 的 22 端口，用私钥或密码登录。
2. **申请反向转发**：调用库的 "remote port forwarding" 接口，把 `(VPS 绑定地址, VPS 端口)`
   映射到 `(本地 host, 本地 port)`。各库对应的关键调用：
   - JSch：`session.setPortForwardingR("0.0.0.0", 9000, "127.0.0.1", 8080)`
     （绑 `0.0.0.0` 仍需服务端 `GatewayPorts`）。
   - Apache MINA SSHD：`session.startRemotePortForwarding(new SshdSocketAddress("0.0.0.0", 9000), new SshdSocketAddress("127.0.0.1", 8080))`。
   - sshj：`ssh.getRemotePortForwarder().bind(new Forward("0.0.0.0", 9000), new SocketForwardingConnectListener(new InetSocketAddress("127.0.0.1", 8080)))`。
3. **保活并保持进程不退出**：开 keepalive；库会在后台自动接收 `forwarded-tcpip` 通道、
   把流量转发到你的本地服务，你不用自己处理每个连接。
4. **自己补的部分**：断线自动重连（重连后要**重新 bind**）、日志/流量统计。

以上整体等价于命令行的 `ssh -N -R 0.0.0.0:9000:127.0.0.1:8080 用户@VPS`。

**路线 B：从零实现（仅供理解，不建议自己搓）**

要自己写 SSH 传输层（版本交换、密钥交换 KEX、加密、MAC 校验）、认证层
（publickey / password），再在连接层实现：发 `tcpip-forward` 全局请求、接收并处理
`forwarded-tcpip` 的通道打开、维护每通道的窗口与数据搬运。工作量约等于写半个 SSH 客户端，
实际项目一律走路线 A。

### 5. 和「花生壳 / frp / ngrok」的异同

**内核思路完全一样**：客户端主动外连到一台公网服务器，用这条出站长连接把入站流量"背"回
内网。区别只在承载通道的协议不同——SSH 用标准 SSH channel；frp / ngrok 用自定义协议
（自带鉴权、心跳、多路复用、按域名路由 HTTP 等）。用 SSH 的好处：VPS 自带 sshd、鉴权
成熟、无需额外部署服务端。

### 6. 服务端那一下（GatewayPorts）到底改了什么

`tcpip-forward` 请求里带的绑定地址，服务端听不听你的，取决于 `GatewayPorts`：
`no`=强制绑 `127.0.0.1`（外网到不了）；`yes`=绑 `0.0.0.0`；`clientspecified`=按请求里的
地址绑。这就是"对公网开放"为什么必须配它的根本原因。
