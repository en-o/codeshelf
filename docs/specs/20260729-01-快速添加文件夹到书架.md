# 快速添加文件夹到书架（Shell 集成）

> 关联 issue：[#54 右键助手](https://github.com/en-o/codeshelf/issues/54)

## 背景

往书架加项目目前只能进应用里手动选路径，路径深的项目尤其烦。用户在文件管理器里已经站在那个文件夹上了，却要切回应用重新找一遍。

issue #54 最初的想法是做「右键助手」，讨论后拆成了两件不相干的事：

- **本 Spec**：文件管理器里右键文件夹 → 加入 CodeShelf 书架。CodeShelf 自己的功能。
- **MouseBoost 类产品**（系统级右键增强工具）：独立仓库、独立产品，与 CodeShelf 零重叠。**不在本 Spec 范围内**，本功能也**不得依赖它** —— 让用户为了加个项目先装第二个 App 并授权辅助功能，不合理。

## 目标

- 拖拽文件夹到 CodeShelf 窗口即可加入书架
- Windows 文件管理器右键文件夹 →「添加到 CodeShelf」，应用已在运行时不起第二个进程
- 三个入口（手动 / 拖拽 / 右键）的校验与去重行为完全一致
- 右键菜单可在设置页开关，卸载时不留注册表垃圾

## Non-Goals

- ❌ 不做 Win11 新式右键菜单的 `IExplorerCommand`（COM 组件、要写 dll）。只写用户级注册表，Win11 用户需点「显示更多选项」——VS Code 同款取舍，接受。
- ❌ 不做 macOS Finder Sync Extension（appex + 签名，成本高）。macOS 侧最多做到 NSServices 服务菜单。
- ❌ 不写系统注册表 HKLM、不要求管理员权限，只用 HKCU。
- ❌ 不做「右键文件 → 用某编辑器打开」等衍生动作，本次只做「加入书架」一件事。
- ❌ 不碰系统级划词 / 全局鼠标钩子 / 辅助功能权限 —— 那是 MouseBoost 的范围。
- ❌ 不做拖拽添加 —— 会破坏 PairDrop 与 Chat 的现有拖放，详见「已知偏差」。

## 方案

### 收敛点（先做，其余都依赖它）

手动、拖拽、命令行三个入口最终调同一个添加函数。校验与去重写在这个收敛点一处，不在每个入口各写一遍（CLAUDE.md 约束 8）。

需要覆盖的边界：路径不存在 / 不是目录 / 无读取权限 / 已在书架（返回已有项目并高亮定位，而非报错或建重复项）。

动手前先 grep 现有添加项目的全部调用者，确认收敛点选在哪一层。

### 入口一：拖拽

`tauri.conf.json` 当前是 `dragDropEnabled: false`，需打开。跨平台、零权限、无前置依赖，性价比最高，先做这条。

风险：开启后会改变 webview 的拖拽事件行为，PairDrop 等已有拖拽交互需要回归确认。

### 入口二：命令行参数（右键菜单的前提）

`src-tauri/src/lib.rs` 已装 `tauri-plugin-single-instance`，但回调里 `_args` 被忽略。需要两条路径都通：

- **热启动**：应用已在运行 → 单实例回调接住参数，交给收敛点，聚焦窗口
- **冷启动**：应用未运行 → 启动流程里读 `std::env::args`

这一环不做，右键菜单点了没反应或起第二个进程。

### 入口三：Windows 右键菜单

用户级注册表两处：文件夹本身的右键，以及文件夹空白处的右键（`Directory\shell` 与 `Directory\Background\shell`），command 指向 exe 并传目录路径参数。

设置页提供注册/注销开关；卸载时清理写入的键。

### 入口四：macOS 服务菜单（可选）

app bundle 声明 `NSServices`，「添加到 CodeShelf」出现在 Finder 右键的「服务」子菜单。零权限零成本，但层级深。**如果拖拽体验足够好，这条可以不做** —— 先看拖拽的实际手感再定。

## 影响面

- 涉及文件/模块：`src-tauri/tauri.conf.json`（dragDropEnabled）、`src-tauri/src/lib.rs`（单实例回调）、项目添加相关 command、设置页前端、Windows 注册表新模块
- **是否涉及 Windows 专有代码**：**是** → 注册表操作在 `#[cfg(target_os = "windows")]` 下，macOS 本地 `cargo check` 根本不编译它。必须走 Docker 交叉编译验证（CLAUDE.md 约束 3）
- 是否涉及数据文件读写：书架数据走现有项目存储路径，若新增写入必须用 `write_atomic` / `parse_json_or_backup`
- **是否改动 Tauri 命令签名**：**大概率是**（注册/注销右键菜单的命令）→ 必须 `cargo test --lib export_bindings` 重新生成绑定，`src/bindings.ts` 禁止手改

## 验证方式

| 项 | 怎么验 |
|---|---|
| 收敛点守卫 | 三个入口分别喂：不存在的路径、文件（非目录）、已在书架的目录 —— 三者行为一致 |
| 拖拽 | 拖文件夹进窗口即入库；顺带回归 PairDrop 的拖拽没坏 |
| 命令行冷启动 | 应用未运行时命令行带参数启动 → 启动后项目已在书架 |
| 命令行热启动 | 应用在运行时再执行一次 → 不起第二个进程，窗口聚焦且项目已加入 |
| Windows 右键 | 注册后在文件夹上和文件夹空白处分别右键（Win11 需展开「显示更多选项」）；注销后菜单项消失，注册表无残留 |
| 编译 | `npx tsc --noEmit`、`cd src-tauri && cargo check`、Windows 交叉编译（约束 3 的 docker 命令）、`cargo test --lib export_bindings` |

## 已知偏差（与原方案不同，动手后才发现）

**拖拽添加不做（2026-07-29 定）。** 原以为把 `dragDropEnabled` 打开即可，实际上它被设成
`false` 是有意的：webview 的 HTML5 拖放依赖这个关闭状态，PairDrop 的文件发送与 Chat 的附件
拖入都在用 `dataTransfer.files`（需要 File 内容，不是路径）。打开开关这两处就收不到 drop 事件。
右键 + 命令行已覆盖「快速添加」的需求，**不值得为一个便利入口去改两个正常工作的功能**。
日后若真要做，代价是把 PairDrop 与 ChatInput 改成由路径经 Rust 读文件，并做实机回归。

**macOS 用「打开方式」而非 NSServices。** NSServices 需要用 objc2 声明一个
Objective-C service provider 类并注册，成本高。改为在 `Info.plist` 声明
`CFBundleDocumentTypes`（public.folder），Finder 右键 →「打开方式」→ CodeShelf 即可添加，
事件走 `RunEvent::Opened`，零 Objective-C 代码。菜单层级与 Windows 的「显示更多选项」同一档。
若日后要进 Finder 右键一级菜单，再考虑 NSServices。

## 附：不属于本 Spec 但已发现的问题

讨论中顺带查出来的，各自独立，别混进本次改动：

1. **prod 环境右键菜单全被禁用** —— `src/main.tsx` 在非 DEV 环境全局 `preventDefault` contextmenu（为挡 Inspect Element），副作用是 prod 下输入框连复制/粘贴/全选都没有；且 dev 与 prod 行为不一致（dev 弹 macOS 原生菜单、Windows 什么都没有），本地测不出线上样子。修的时候注意：粘贴需要读剪贴板，前端只用过 `writeText`，webview 的 `readText` 受权限限制，稳妥做法是在 `toolbox/clipboard.rs` 补一个读命令（剪贴板监控本来就在读，能力现成）。
2. **三份重复的右键菜单实现** —— `EditorContextMenu.tsx`、`TerminalContextMenu.tsx`、`PairDrop.tsx` 各写一套，都自己实现了「点外面关闭 + ESC 关闭 + 防溢出定位 + 动画」。可抽 `src/components/ui/ContextMenu.tsx` 承接，纯重构，优先级最低。
3. **MouseBoost 类产品的两个前置 spike**（独立仓库，先验证再谈产品形态）：能否吞掉原生右键并在未达触发时长时原样补发；浮层能否不抢焦点（抢了焦点前台 App 就丢选区，「复制选中文字」这类动作全废）。
