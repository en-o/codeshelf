# 网络环境一致性检测整合评估

> 状态：调研结论，尚未批准实施
>
> 参考项目：`detect-radar`（调研时位于 CodeShelf 仓库外）
>
> 结论：**有产品价值，建议选择性整合；不建议整站、整套后端或现有评分原样迁入。**

## 背景

DetectRadar 的“雷达”不是主动扫描附近网络，也不是漏洞扫描器。它把当前出口 IP、浏览器环境、DNS、WebRTC、IPv6 和公开信誉信息汇总成一份一致性报告，再用雷达图展示几个维度。

它实际回答的问题是：

> 外部网站现在看到的网络身份是什么？VPN、代理、DNS、IPv6 和浏览器环境之间有没有明显矛盾？

这个能力对 CodeShelf 用户有用，尤其适合以下场景：

- 切换 Wi-Fi、VPN、代理或网络节点后，确认出口 IP、地区和 ASN 是否真的变化。
- 排查 DNS、WebRTC 或 IPv6 是否绕过了预期代理。
- 保存切换网络前后的诊断快照，向团队或技术支持提供脱敏报告。
- 整合进 CodeShelf 后，可进一步增加 GitHub、npm、Crates、Maven、AI 服务等开发站点的 DNS、TCP、TLS 和证书诊断；这部分是拟新增能力，不是 DetectRadar 的现成功能。

它**不能**加速网络、修改代理、隐藏身份、修复指纹，也不能证明任何账号不会被平台风控。现有总分是项目自定义启发式规则，不是行业安全等级。

## 调研结论

### 是否值得做

**值得，但需要重新定位。**

CodeShelf 中建议使用“网络环境诊断”或“网络环境体检”，面向开发排障；不使用“防关联”“纯净度”“风控安全”等容易过度承诺的定位。

### 是否能直接搬

**不能直接搬，原因不是界面，而是检测位置和基础设施不同。**

| 方案 | 结果可信度 | 成本 | 结论 |
|---|---:|---:|---|
| 把 DetectRadar 页面塞进 CodeShelf WebView | 低 | 中 | 不采用；测到的是 CodeShelf WebView，不是用户实际浏览器 |
| 把 Go 服务改成本地 sidecar | 低 | 高 | 不采用；本地服务看到的主要是本机连接，无法替代公网观察点和权威 DNS |
| 仅做 CodeShelf 本地网络诊断 | 中 | 中 | 采用；适合系统代理、DNS、路由、连通性和历史对比 |
| 默认浏览器 + 远程探针 + CodeShelf 回收结果 | 高 | 中到高 | 推荐的完整形态 |
| 原样部署完整 DetectRadar 服务 | 取决于数据与运维 | 高 | 可作为参考服务，不作为桌面端直接迁移方案 |

CodeShelf 在 `src-tauri/tauri.conf.json` 中固定了 `CodeShelf-Tauri-Webview/1.0` User-Agent。内嵌采集得到的是 WKWebView、WebView2 或 WebKitGTK 的环境；Canvas、WebGL、插件、自动化等结果不能代表用户正在使用的 Chrome、Firefox 或 Edge。

当前安全配置也不支持直接嵌入：CodeShelf 的 CSP 禁止 frame，且未放行 DetectRadar API 和动态 FingerprintJS 脚本；DetectRadar 后端 CORS 只允许其站点域名。放宽这些限制仍然解决不了“检测对象是 WebView”的根本问题，因此不作为迁移方向。

## 目标

- 在工具箱提供面向开发者的网络环境诊断入口。
- 明确区分本机观测、默认浏览器观测、远程服务观测和第三方情报。
- 支持 VPN、代理或网络切换前后的快照对比。
- 对无法检测、未配置、请求失败和确认正常使用不同状态，禁止“测不到即正常”。
- 仅在用户主动开始检测后访问远程探针，并清楚展示会提交的数据。
- 每个结论展示数据来源、检测时间和判断依据，避免只给一个不可解释的分数。

## Non-Goals

- ❌ 不做 VPN、代理、网络加速或自动修复工具。
- ❌ 不承诺绕过平台风控、避免账号关联或证明网络“绝对安全”。
- ❌ 不在 CodeShelf WebView 中声称检测了用户的真实浏览器指纹。
- ❌ 不把 FingerprintJS Visitor ID、Canvas/Audio 跟踪标识作为默认能力。
- ❌ 不把共享的第三方 API Key、商业数据库或 DNS 基础设施打包进桌面客户端。
- ❌ 不把公网 IP 上的开放端口描述为“当前电脑开放端口”；NAT、CGNAT 和第三方快照都可能使两者无关。
- ❌ 不原样复制 DetectRadar 名称、Logo、整套 UI、服务条款或营销文案。
- ❌ 不在第一阶段建设权威 DNS、DNSTap、Redis 和完整 IP 情报平台。

## 原项目能力核对

| 检测项 | 实际依据 | 可提供的价值 | 迁入判断 |
|---|---|---|---|
| 出口 IP | 后端读取请求连接的公网来源地址 | 确认 VPN/代理是否生效 | 保留，需要公网观察点 |
| 地区、ASN、运营商 | MMDB、ip2region 或第三方 API | 解释出口归属 | 保留，但必须标数据源和时间 |
| 住宅/机房/代理判断 | 云厂商 CIDR、ASN、反向 DNS、组织名和第三方结果合并 | 提示出口类型 | 降级为“情报提示”，不能当身份事实 |
| 黑名单、Tor、开放端口 | DNSBL、Tor 列表、Shodan InternetDB 等第三方快照 | 辅助排查服务拒绝 | 后续可选；显示来源、时间和不确定性 |
| 时区一致性 | 浏览器时区与 IP 时区的当前 UTC 偏移比较 | 发现明显地区矛盾 | 保留；不同 IANA 时区可能在当时偏移相同 |
| 语言一致性 | 浏览器语言与手写国家语言表比较 | 低权重提示 | 可选，不进入高风险结论 |
| WebRTC | Google STUN 返回 ICE 候选，再与出口 IP 比较 | 发现浏览器旁路 | 只在默认浏览器探针中保留 |
| IPv6 | 复用 WebRTC 中的全局 IPv6 候选 | 提示可能存在另一条出口 | 需要改成独立 IPv4/IPv6 请求验证 |
| DNS | 自有权威域名和 DNSTap 观察递归解析器 | 发现 DNS 路径异常 | 有价值，但必须先建设远程基础设施并修正规则 |
| Canvas、Audio、WebGL | 哈希、Renderer 和原生函数字符串检查 | 反指纹/自动化环境的弱提示 | CodeShelf 默认不迁；与开发网络排障关联弱 |
| 自动化 | `navigator.webdriver`、插件数等 | 自动化测试环境自检 | 默认不迁；WebView 中噪声大 |
| RTT | 浏览器请求耗时、可选 nginx TCP RTT | 展示到远程探针的延迟 | 可保留为读数，不参与首版评分 |
| 雷达图与总分 | 手写规则扣分并按维度封顶 | 快速汇总 | 图可借鉴；现有分值不能原样使用 |
| 分享卡 | 浏览器本地绘图并脱敏 IP | 便于协作排障 | 后续保留，优先支持结构化脱敏导出 |

## 已发现的功能缺陷

以下问题在迁移前必须重新定义，不能把现有结论和文案直接复制到 CodeShelf。

### 阻断级

1. **DNS 结论文案与实际算法不一致**

   页面声称“DNS 与出口 IP 地区不一致”，但 `server/internal/service/dns.go` 没有把 DNS 解析器国家与本次出口 IP 国家进行比较。当前主要依据是：

   - 公共 DNS 与本地 ISP DNS 同时出现；
   - 解析器来自多个国家；
   - ISP 数量较多。

   这些现象可以提示路径复杂，不能直接证明 DNS 绕过了代理。`client/src/lib/report.ts` 的现有文案过度推断。

2. **缺失数据可能被显示为正常**

   WebGL、Canvas、Audio、硬件、信誉等部分信号缺失或服务未配置时，现有逻辑可能落到绿色、100 分、“0/100 很低”或“未命中”。这会把“未知”误报成“安全”。

3. **内嵌后检测对象错误**

   浏览器类信号只描述运行采集代码的容器。直接放进 CodeShelf 后，报告描述的是 CodeShelf WebView，不能代表用户要排查的目标浏览器。

4. **完整检测并非纯前端能力**

   出口 IP、ASN/地区、DNS 递归路径、远端 RTT 和信誉信息都依赖公网观察点、数据库或第三方 API。没有这些依赖时无法复现截图中的完整报告。

### 高优先级

5. **IPv6 不是独立连通性检测**

   当前 IPv6 主要来自 WebRTC 候选。浏览器阻止候选不等于没有 IPv6，检测到 IPv6 也不等于它绕过代理。应使用独立 IPv4、IPv6 探针核对实际出口。

6. **评分缺少校准依据**

   总分和四个维度来自手写权重，例如机房、代理、语言、自动化分别扣固定分。规则可以帮助排序问题，但没有样本校准、误报率或外部标准，不能叫“安全分”或“风控分”。

7. **第三方无数据与“干净”混淆**

   欺诈分只由可选适配器提供；黑名单、Shodan 或 Tor 查询也可能关闭、超时或过期。所有外部情报必须同时返回查询状态（成功、不可用、失败）和命中状态（命中、未命中、未评估），不能只返回空数组或零。

8. **数据新鲜度不可见**

   ASN、云厂商网段、开放端口、黑名单和 Tor 信息都有更新周期。现有报告没有统一展示数据源、抓取时间和缓存命中情况。

9. **隐私模型不适合桌面工具默认行为**

   参考项目会向后端提交出口 IP、环境信号和指纹哈希，并保留扫描判定快照。CodeShelf 不能进入页面即自动上传；需要主动开始、最小采集、明确用途和可删除策略。

### 中优先级

10. **多项信号采集后没有参与结论**

    FingerprintJS Visitor ID、Audio 哈希、WebGL 图像哈希与扩展、屏幕高熵字段、方向/陀螺仪/电池等数据被采集，但没有形成有效分析，增加了复杂度和隐私面。

11. **部分展示能力仍是预留**

    `ecommerce`、`social` 场景、JA3/TLS/QUIC 指纹、完整移动环境仿真、完整硬件逻辑等尚未形成可用流程，不能计入迁移范围。

12. **修复建议生成了但没有完整展示**

    报告模型包含“事实、含义、修复方法”，当前主要界面和分享图没有完整呈现。对 CodeShelf 而言，可执行的排障建议比雷达分数更重要。

13. **工程成熟度不足**

    参考仓库提交历史很短，未跟踪测试文件；运行所需 `data/`、`docs/`、`server/scripts/` 和 `*_test.go` 还被 `.gitignore` 排除。不能视为可直接嵌入的成熟模块。

## CodeShelf 应补充的能力

参考项目偏向“代理/浏览器环境自洽”，CodeShelf 应补上更贴近开发工作的诊断项。

### 本机基础诊断

- 当前活动网卡、默认路由、IPv4/IPv6 地址与网络变化时间。
- 系统代理与 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` 等开发环境代理。
- 操作系统 DNS 服务器、域名解析结果与解析耗时。
- 本地端口占用、代理端口连通性与 CodeShelf 现有系统监控的跳转关联。
- 离线、DNS 失败、TLS 失败、代理拒绝、连接超时等错误分类。

### 开发服务连通性

- GitHub、npm、Crates、Maven 等常用开发服务的 DNS、TCP、TLS 和 HTTP 可达性。
- 用户配置的 API 域名或镜像源检测，避免把固定服务列表写死。
- 证书颁发者、有效期、主机名不匹配和系统时间异常提示。
- 默认只检测应用按当前系统与环境配置实际使用的网络路径，不自动禁用或绕过代理。
- “直连与代理对比”只能作为用户明确授权的高级探针，并限制为公开目标；不得因 `NO_PROXY` 或目标配置错误而意外直连内网地址。

### 历史与协作

- 保存“切换前 / 切换后”两次网络快照并突出变化项。
- 每项结果带检测时间、数据来源、状态和简短解释。
- 导出默认脱敏的 JSON 或图片；完整 IP 必须由用户主动选择显示。
- 历史默认仅保存在本地，支持单条删除和全部清除。

这些能力比 Canvas、Audio、Visitor ID 或自动化痕迹更符合 CodeShelf 的开发者工具定位。

## 状态模型

执行状态与结论状态必须分开保存，避免“测不到即正常”，也避免把请求失败误当成检测结论。

### 执行与证据状态

| 状态 | 含义 |
|---|---|
| `not_checked` | 用户尚未开始或该项尚未执行 |
| `observed` | 本次成功获得可解释的新数据 |
| `no_hit` | 名单类数据源查询成功且明确未命中 |
| `stale` | 只有超过有效期的缓存数据 |
| `unsupported` | 当前平台、浏览器或部署没有这项能力，例如未建设 DNS 探针 |
| `unavailable` | 已配置的外部数据源暂时不可用 |
| `failed` | 本应可执行，但网络、权限、解析或协议失败；完全离线的远程项属于此状态 |

### 解释状态

| 状态 | 含义 |
|---|---|
| `normal` | 有新鲜、完整证据，且符合当前明确规则 |
| `warning` | 有新鲜、完整证据，发现需要核对的差异 |
| `unknown` | 证据不足、过期、冲突，或当前规则不能给出结论 |

`unsupported`、`unavailable`、`failed` 和 `stale` 默认只能映射为 `unknown`，不能映射为 `normal`。“未命中黑名单”必须同时满足查询成功、数据源可用和 `no_hit`；“未检测到 IPv6”必须区分没有 IPv6、浏览器不暴露候选和探针不可用。

## 推荐方案

### 第一阶段：本地诊断 + 浏览器深度检测入口

在 CodeShelf 工具箱新增“网络环境诊断”：

- CodeShelf 本地完成网卡、路由、系统代理、环境变量代理、系统 DNS 和开发服务连通性检查。
- 本地模式只描述本机地址、路由和配置的 DNS，不声称已经验证公网 IPv4/IPv6 出口或 DNS 递归路径。
- 需要浏览器环境的检查通过现有 `open_url` 在默认浏览器打开。
- 第一阶段只允许打开固定、不带动态参数的 HTTPS 探针地址。
- 如果尚未建设 CodeShelf 自有探针，打开现有 DetectRadar 只能作为临时验证入口，不算功能已迁入。
- 首版不展示总风险分；使用问题清单、状态和检测覆盖率。

### 第二阶段：一次性检测任务

建设 CodeShelf 自有浏览器探针和版本化任务接口。现有 DetectRadar `/scans` 由客户端提供扫描标识、结果只在服务内短期保存且没有任务所有权鉴权，**不能直接作为 CodeShelf 的结果交接协议**。

1. CodeShelf 通过 Rust 网络层创建任务，得到任务 ID、仅供浏览器提交的短期写能力和仅由桌面端持有的读凭据。
2. 默认浏览器打开固定探针域名；写能力通过不会进入 HTTP Referrer 的交换流程传递，交换后立即从浏览器地址和历史中移除。
3. 浏览器和公网服务完成各自观测，写能力只允许提交一次且不能读取结果。
4. CodeShelf 通过 Rust 网络层使用读凭据轮询结构化摘要，不依赖 WebView CORS，也不把读凭据暴露给浏览器。
5. 任务完成并被桌面端取回后销毁，未完成任务在短 TTL 后过期；日志不得记录凭据或完整任务 URL。
6. 用户切换网络后再次检测，CodeShelf 在本地展示前后差异。

读写凭据都必须具备足够熵、URL 安全、权限隔离、过期和重放防护。探针页使用 `Referrer-Policy: no-referrer`；远程服务默认不长期保存完整 IP 或浏览器指纹。

这一阶段还需要两个自有公网协议探针：A-only/IPv4 端点与 AAAA-only/IPv6 端点，才能独立验证双栈出口，不能继续只复用 WebRTC 候选。

### 第三阶段：可选高级探针

只有在确有使用量并接受运维成本后再考虑：

- 自有权威 DNS 与 DNSTap 检测；只有建成后才能比较 VPN 切换前后的 DNS 递归路径。
- 多地区 RTT 探针。
- 带数据源时间戳的 ASN、Tor、DNSBL 和信誉信息。
- 脱敏分享卡和团队排障链接。

## 展示原则

- 雷达图可以作为概览，但每个轴必须能展开到证据；未知项不能贡献满分。
- 首版不提供“纯净度”“欺诈风险”“账号安全”总分。
- IP 类型只显示“数据源判断为住宅/移动/托管/未知”，不推导账号可信度。
- DNS、WebRTC、IPv6 结论分别描述观测事实，不笼统写“真实 IP 已泄露”。
- 开放端口必须标注为第三方历史快照，不能冒充本次主动扫描。
- 所有建议优先回答“下一步怎么核对”，不自动修改系统网络设置。

## 数据与隐私

- 进入工具页不自动访问第三方服务；用户点击开始前展示远程检测说明。
- 本地模式不上传网卡地址、代理凭据、环境变量值或项目配置。
- 对 URL 中可能含 token、用户名、密码的代理配置先脱敏，再展示或导出。
- 浏览器探针只采集形成明确结论所需的字段，不采 Visitor ID。
- 使用 IP 情报、DNSBL、Shodan、Team Cymru 等查询时，第三方会收到用户公网 IP 或可还原该 IP 的查询值；开始前必须逐项披露数据接收方和用途，不能只笼统提示“需要联网”。
- 远程结果设置短保留期；历史报告由 CodeShelf 本地保存。
- 导出时默认遮盖公网 IP、局域网 IP、主机名和可能识别用户的网络名称。

- DetectRadar 服务条款另行限制名称、界面和内容的商业再分发。最稳妥的范围是复用通用算法思路或有明确归属的源码，不复制名称、Logo、整套 UI 和原文案。
- MIT 不自动覆盖 MMDB、ip2region、云厂商网段、Shodan、DNSBL、Tor 列表、Team Cymru、Cloudflare Radar 和各 IP API 的数据或服务条款。
- Google STUN、FingerprintJS CDN 和外部 API 都会产生远程请求；采用前必须逐项确认隐私、配额、CORS、可用性和再分发条件。
- 第三方 API Key 不得进入前端包或桌面应用资源。

## 影响面

- 涉及文件/模块：
  - `src/pages/Toolbox/index.tsx`：工具入口和页面路由。
  - `src/types/toolbox.ts`：工具类型与诊断结果类型。
  - `src/services/toolbox/index.ts`：Tauri 命令封装。
  - `src-tauri/src/commands/toolbox/`：本机网络诊断命令。
  - `src-tauri/src/handlers.rs`：命令注册。
  - `src-tauri/tauri.conf.json`：仅在确有需要时调整连接白名单；不为动态脚本放宽 CSP。
  - 每用户可写的应用数据目录或现有 SQLite：本地诊断历史。
- 是否涉及 Windows 专有代码：**是**。系统代理、DNS、路由读取存在平台差异，需要 Windows 交叉编译和实机验证。
- 是否涉及数据文件读写：**是**。网络历史落盘前必须先完成 `REMEDIATION.md` 的 AUD-023 所述存储纠偏：Linux 使用每用户数据目录，Windows 明确区分安装版与便携版，并为安装版选择确定可写的位置；在此前历史只能保存在内存或保持关闭。若历史使用 JSON，必须走 `write_atomic` / `parse_json_or_backup`；若使用现有 SQLite，则需要迁移测试和并发策略。
- 是否改动 Tauri 命令签名：**是**。实现时必须重新生成 bindings，禁止手改 `src/bindings.ts`。
- 是否涉及远程协议：第二阶段开始涉及。必须先写清 API 版本、token 生命周期、数据保留和错误状态。

### 前置整改

- 第二阶段打开动态任务 URL 前，必须先完成 `REMEDIATION.md` 的 AUD-005：不再通过 Windows `cmd /c start` 处理 URL，改用不经过命令解释器的系统打开能力，并严格限定 `https`、固定 host 和 URL-safe 参数。
- 本地历史落盘前必须先完成 AUD-023，统一到真正可写、可迁移的每用户数据目录。

## 验证方式

| 阶段 | 场景 | 验收结果 |
|---|---|---|
| 第一阶段 | 完全离线 | 本地信息仍可查看；本应可用的远程项显示 `failed`，尚未部署的能力显示 `unsupported`，都不显示绿色正常 |
| 第一阶段 | VPN 关闭 / 开启各测一次 | 本地路由、系统代理和配置 DNS 的变化能被准确突出；不声称已验证公网出口或 DNS 泄露 |
| 第一阶段 | 系统代理含凭据 | 页面、日志和导出均不出现明文用户名、密码或 token |
| 第一阶段 | 固定浏览器入口 | 只打开固定 HTTPS 地址，不接受任意远程跳转 |
| 第二阶段 | VPN 关闭 / 开启各测一次 | 公网出口 IP、地区、ASN 和 IPv4/IPv6 出口变化能被准确突出 |
| 第二阶段 | 仅 IPv4、仅 IPv6、双栈 | A-only 与 AAAA-only 探针能区分三种情况；WebRTC 不作为唯一 IPv6 依据 |
| 第二阶段 | 浏览器阻止 WebRTC | 显示不支持或未知，不显示“未泄露” |
| 第二阶段 | 任务鉴权 | 写能力不能读取、不能重复提交；读凭据不进入 URL、Referrer、浏览器历史或日志，过期任务不能访问 |
| 第二阶段 | IP 情报 API 超时 | 地区、ASN、信誉分别显示 `unavailable` 或 `failed`，不能回退为 0 分或未命中 |
| 第二阶段 | 默认浏览器检测 | 报告明确标识浏览器名称；不使用 CodeShelf WebView 的结果冒充目标浏览器 |
| 第三阶段 | DNS 探针未部署 / 已部署 | 未部署时显示 `unsupported`；部署后才验收递归 DNS 观测和 VPN 前后路径变化 |
| 历史启用后 | 历史对比 | 可保存两次快照、查看变化，并能删除单条或全部历史；目标目录在各平台可写 |
| 全阶段 | 数据来源 | 每个远程结论可看到来源、观测时间和是否命中缓存 |
| 全阶段 | 跨平台 | macOS、Windows、Linux 对不支持项返回一致语义，不用空值冒充成功 |
| 全阶段 | 回归 | 工具箱现有系统监控、端口扫描、下载、隧道和 PairDrop 不受影响 |

实现阶段的基础验证至少包括：

- `npx tsc --noEmit`
- `cd src-tauri && cargo check`
- `cd src-tauri && cargo test`
- `cd src-tauri && cargo test --lib export_bindings`
- Windows 交叉编译与 macOS、Windows 实机网络切换验证

## 实施前待确认

1. 是否愿意维护 CodeShelf 自有公网探针服务；如果不维护，功能必须明确为“本地诊断精简版”。
2. 是否需要检测用户默认浏览器；如果需要，采用外部浏览器探针，不在 WebView 内做指纹结论。
3. 网络历史是否默认开启，以及默认保留数量和删除策略。
4. 首版开发服务连通性内置哪些目标，哪些由用户自定义。
5. 是否接受第三方 IP 情报、STUN 或 DNS 服务产生的远程请求。
6. 是否仅借鉴设计，还是复制部分 MIT 源码；后者需要先建立第三方许可证清单。
7. AUD-005 和 AUD-023 是否先于第二阶段、历史功能进入整改排期。

在以上问题确认前，本 Spec 只作为整改和产品决策依据，不进入功能实现。
