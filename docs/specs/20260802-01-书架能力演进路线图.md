# 书架能力演进路线图

> 状态：规划中，尚未进入功能实现
> 基线：`dev` / CodeShelf v0.1.44（2026-08-02）
> 首个实施候选：不依赖 AI 的跨项目本地搜索

M1 已拆出实施规格：[M1：跨项目本地搜索](20260802-02-跨项目本地搜索.md)。本路线图继续负责完整能力范围与里程碑顺序，M1 的接口、资源常量和验收细节以独立 Spec 为准。

## 背景

CodeShelf 当前书架已经完成单项目管理的主体闭环：项目入库、分类与标签、收藏、Git 状态、分支与远程仓库、提交/拉取/推送、README、编辑器/终端/Claude Code 快捷入口，以及绑定项目目录的 AI 对话。

现阶段真正缺少的不是继续往卡片上增加字段，而是三类跨越单项目边界的能力：

1. **跨项目发现**：在多个仓库中搜索代码、文件、配置和依赖。
2. **项目运行**：基于明确证据识别项目环境，并以受管方式启动、观察和停止项目。
3. **联合开发**：在运行器稳定后，将多个需要共同运行的项目组织成可执行的开发场景。

同时，CodeShelf 已有 AI 供应商、项目对话和项目背景知识能力，但用户可能完全不配置 AI。因此，后续书架能力不得把 AI 变成基础依赖。

现有实现依据：

- 项目模型已有分类、标签、最近打开、编辑器和 Claude 环境字段：`src/types/index.ts`、`src-tauri/src/storage/schema.rs`
- Git 状态已有待提交、冲突、待推送、待拉取信息：`src/types/index.ts`、`src-tauri/src/commands/git/`
- 项目对话通过 `allowedCwd` 将工具限制在单个项目目录：`src/components/project/ProjectDetailPanel.tsx`、`src-tauri/src/commands/tools/ctx.rs`
- AI Shell 已有超时、输出上限和进程树清理，但定位是短时工具调用，不适合常驻开发服务：`src-tauri/src/commands/tools/shell.rs`
- 简历 Agent 已实现遵循 `.gitignore`、敏感文件规则和项目根路径边界的 `ls/glob/grep/read`：`src-node/resume-agent/src/fs/projectBackend.ts`
- 项目背景知识已经独立持久化为 Markdown：`src/types/resume.ts`、`src/services/resume/knowledgeStore.ts`

## 核心决策

### DEC-001：AI 是可选增强，不是功能依赖

所有核心功能先产生完整的本地确定性结果，AI 只能在用户主动操作后读取经过裁剪的结果并生成附加内容。

必须满足：

- 未配置 AI 时，跨项目搜索、依赖解析、环境识别、项目运行和开发场景均可正常使用。
- 配置 AI 后也不自动调用模型；由用户点击“智能扩展”“AI 解释”“生成说明”等显式入口。
- AI 失败、超时、余额不足或供应商被删除时，本地结果保持可见、可操作。
- 本地结果与 AI 结果分开保存、分开展示；AI 结果不得覆盖确定性事实。
- 发送给 AI 的内容必须可预览，并继续受敏感文件规则约束。

统一数据流：

```text
本地输入 → 本地引擎 → LocalResult → 直接展示与操作
                              └→ 用户主动请求 → AiEnhancement
```

### DEC-002：分类不改造成第二套“工作区”

分类继续承担整理和筛选职责。不新增一个只有名称和成员列表的“工作区”，因为这与分类重复。

只有在项目运行器稳定以后，才考虑新增“开发场景”：

- 成员可以从现有分类中选择，但不等同于整个分类。
- 成员具有前端、后端、基础设施、文档等角色。
- 场景保存启动顺序、运行方案、就绪检测和停止顺序。
- 场景的验收重点是联合执行；仅能分组不算完成。

如果实际使用中分类已经一一对应完整业务系统，且没有联合启动需求，则开发场景可以不实施。

### DEC-003：跨项目搜索首先是本地搜索器

首版搜索不调用 AI、不建立向量库、不做全量内容常驻索引。

- 明确文本、正则、文件名由本地搜索引擎处理。
- 依赖和运行时版本由清单文件解析器处理。
- Git 项目优先搜索已跟踪文件；非 Git 或需要未跟踪文件时再走受控文件遍历。
- AI 后续只能负责扩展候选关键词或归纳已经命中的少量片段。

### DEC-004：环境检测和进程执行分阶段交付

“识别出项目可能怎么运行”和“真的启动一个长期进程”是两件事，不在同一阶段一口气完成。

1. 先只读检测项目证据和本机环境，输出可解释报告。
2. 再允许用户确认、修正并保存运行配置。
3. 最后由独立受管进程服务启动、停止和回收长期进程。

不得：

- 自动安装 JDK、Node、Rust、Python、Maven、Nginx 等软件。
- 自动修改系统级 `PATH`、`JAVA_HOME`、默认 Node/Python 或全局代理。
- 在检测证据冲突时猜一个版本直接运行。
- 直接复用 AI Shell 执行器托管长期开发服务。

### DEC-005：一次只推进一个可验收里程碑

本路线图是范围和顺序的唯一真相源，不是一次性实施授权。每个涉及跨模块、存储迁移或新的进程生命周期的里程碑，开始编码前另写独立 Spec。

下一阶段只有在上一阶段达到验收门槛后才启动，不同时铺开多个里程碑。

## 目标

- 建立不依赖 AI 的跨项目本地搜索能力。
- 建立低内存、可取消、有确定上限的搜索执行模型。
- 建立基于项目文件与本机版本核验的环境检测能力。
- 建立不修改全局环境的项目级运行配置。
- 建立可观察、可停止、应用退出时可回收的受管进程服务。
- 在单项目运行稳定后，评估并实现可联合启动的开发场景。
- 将现有项目分析能力沉淀为书架中的项目知识库与自动说明书。
- 建立多远程代码备份与镜像状态管理。
- 建立区分逻辑归档与磁盘冷藏的可恢复项目生命周期。
- 支持从现有项目安全地创建新项目，并完成变量替换、Git 初始化和书架入库。
- AI 配置存在时提供可选增强，缺失时功能无降级。

## 完整功能清单与路线映射

本路线图覆盖讨论中确认的全部七项产品能力，并单列横向的可选 AI 增强。部分能力为控制风险被拆成多个技术里程碑，但产品名称必须保持可追踪。

| 产品能力 | 路线落点 | 核心产物 |
|---|---|---|
| 跨项目代码与依赖搜索 | M1 + M2 | 本地文本/正则/文件搜索、结构化依赖清单搜索 |
| 项目运行中心 | M3 + M4 | 只读环境检测、项目运行配置、受管长期进程 |
| 多项目工作区 | M5 | 具备角色、顺序、就绪检测和联合启停的开发场景 |
| 可选 AI 增强 | M6 | 搜索扩词/归纳、环境解释、知识说明；无 AI 不降级 |
| 项目知识库 / 自动说明书 | M7 | 可追溯证据、基础说明书、版本与过期状态、可选 AI 内容 |
| 代码备份与镜像中心 | M8 | 备份策略、远程镜像、执行记录与恢复验证 |
| 冷藏书架 / 项目归档 | M9 | 逻辑归档、磁盘冷藏、完整性校验与恢复 |
| 从现有项目创建新项目 | M10 | 模板快照、变量预览、安全复制、初始化与入库 |

其中“多项目工作区”保留用户熟悉的产品名称，但只实现有联合执行价值的版本；内部和界面副标题可使用“开发场景”解释其与分类的区别。

## Non-Goals

- ❌ 不做离开 AI 就无法使用的自然语言搜索、环境检测或项目运行。
- ❌ 首版不做代码 Embedding、向量数据库、全量语义索引。
- ❌ 首版不做跨项目批量替换或自动修改代码。
- ❌ 首版不启动各语言的 LSP 来做精确引用分析。
- ❌ 不将分类复制成只有成员列表的“工作区”。
- ❌ 不做通用 IDE、完整 CI/CD 平台或系统级版本管理器。
- ❌ 不负责自动下载和安装开发环境。
- ❌ 不承诺一次覆盖所有构建工具、版本管理器和操作系统差异。
- ❌ 备份中心不承诺替代专业 Git 托管、云备份或灾难恢复平台。
- ❌ 冷藏书架不在工作区不干净、备份未确认时自动删除项目目录。
- ❌ 从现有项目创建新项目不做任意脚本执行型模板市场。

## 总体分层

```text
书架与项目详情 UI
       │
       ├── 跨项目搜索结果
       ├── 项目知识与说明书
       ├── 环境检测报告
       ├── 单项目运行状态
       ├── 多项目工作区状态
       ├── 备份与镜像状态
       ├── 归档与恢复状态
       └── 从现有项目创建向导
       │
本地确定性能力层
       ├── Project Search
       ├── Manifest Parsers
       ├── Project Knowledge Builder
       ├── Runtime Detector
       ├── Managed Process Runner
       ├── Git Mirror Manager
       ├── Project Archive Manager
       └── Project Template Creator
       │
现有项目、Git、文件系统、Docker 与进程能力

可选 AI 增强层只读取上层已经产生并裁剪的 LocalResult。
```

模块边界原则：

- 搜索模块不读取 AI Provider Store。
- 环境检测模块不调用模型，也不执行安装命令。
- 运行器不负责判断“应该使用哪个环境”；它只执行用户确认过的运行配置。
- 开发场景不直接拼接任意 Shell；它编排已经验证过的单项目运行配置。
- 知识库的确定性信息来自清单、Git、README 和目录证据；AI 内容单独标识。
- 备份、冷藏和项目创建共用路径校验、进度、取消、失败对账和恢复验证原则。
- AI 增强不持有进程控制权，不直接触发启动、停止、安装或批量修改。

## 分阶段路线图

### M1：跨项目本地搜索

#### 目标

用户可以从整个书架、指定分类或手选项目中，搜索明确文本、正则和文件名，并实时查看按项目/文件分组的结果。

#### 首版范围

- 搜索模式：文本、正则、文件名。
- 搜索范围：全部项目、分类、手选项目。
- 文件范围：全部文本文件或用户指定 glob。
- 默认只搜索 Git 跟踪文件；可显式选择包含未跟踪文件。
- 每条结果包含项目、相对路径、行号、命中预览。
- 支持打开所属项目、复制路径和在编辑器中打开文件。当前编辑器接口没有能力协议，M1 不承诺跳转行号；先提供复制“路径:行号”。
- 搜索结果流式分批返回，支持取消。
- 错误按项目隔离：一个项目失败不终止全部搜索。

#### 资源边界

首版默认值，独立 Spec 可根据原型测量调整：

- 默认并发搜索 2 个项目，上限 4 个。
- 单项目最多返回 500 条，全局最多 2,000 条。
- 不把完整文件读入长期缓存，不在前端保存完整文件内容。
- 结果按小批次发送，避免每命中一行触发一次 IPC 和 React 更新。
- 搜索任务有唯一 ID、取消信号和超时上限。
- 忽略 `.git`、`node_modules`、`target`、`dist` 等生成目录，并遵循项目 `.gitignore`。现有敏感规则只服务背景知识生成，M1 不用它静默过滤测试、CI 和应用配置；未来 AI 出站时再过滤。

#### 有意不做

- 不调用 AI。
- 不做自然语言意图理解。
- 不做搜索结果批量替换。
- 不持久化全量文件内容索引。
- 不将简历 Agent sidecar 直接扩成通用搜索服务；可复用其边界设计，但避免让书架搜索依赖简历模块存活。

#### 验收门槛

- AI Provider 为空时完整可用。
- 50 个中小型项目范围内搜索时，内存不会随累计读取文件总量线性增长。
- 搜索中途取消后，子进程或遍历任务及时退出，不继续占用 CPU。
- 某项目路径失效、无权限或不是 Git 仓库时，其他项目仍正常返回结果。
- 中文路径、空格路径、大小写敏感选项和二进制文件行为明确。
- 结果上限触发时明确提示“结果已截断”，不冒充完整结果。

#### 实施规格

[M1：跨项目本地搜索](20260802-02-跨项目本地搜索.md) 已确认：

- 从书架“更多”菜单进入全屏覆盖层，现有项目名/路径搜索框语义不变。
- Git 项目默认只搜索跟踪文件，可显式包含未跟踪但未忽略文件；非 Git 项目走受控遍历。
- 首版不保存搜索历史，不承诺编辑器跳行。
- 请求、流式事件、终态、任务所有权、取消、应用退出清理和资源上限。

### M2：依赖与运行时清单搜索

#### 目标

在不扫描全部源代码的情况下，回答“哪些项目使用某依赖/版本/运行时”。

#### 范围

按批次增加清单解析器：

1. Maven / Gradle：`pom.xml`、`build.gradle`、版本目录。
2. Node：`package.json`、`packageManager`、锁文件、`engines`。
3. Rust：`Cargo.toml`、`Cargo.lock`、`rust-toolchain.toml`。
4. Python：`pyproject.toml`、`requirements.txt`、常见锁文件。
5. Go：`go.mod`。

输出必须保留证据文件、字段路径和原始版本文本，不只给归纳后的标签。

#### 有意不做

- 不联网查询漏洞库或依赖最新版本。
- 不自动升级依赖。
- 不用 AI 解析结构化清单。
- 不承诺首版解析所有构建脚本中的动态表达式；无法确定时标记 `unknown` 并展示证据。

#### 验收门槛

- 依赖查询只读取相关清单，不遍历全部源码。
- 同一依赖在父 POM、直接依赖、开发依赖等不同来源中不混为一谈。
- 解析失败与“没有该依赖”严格区分。

### M3：只读环境检测

#### 目标

从项目文件和本机实际版本中形成可解释的环境检测报告，不执行项目、不修改环境。

#### 检测流水线

```text
项目证据 → 版本要求 → 本机候选环境 → 匹配结果 → 用户确认
```

每个结论必须包含：

- 证据来源，例如 `pom.xml` 的 Java 版本、`.nvmrc`、`rust-toolchain.toml`。
- 需要的运行时、构建工具和包管理器版本。
- 本机发现的候选可执行文件、实际版本和来源。
- 状态：`ready`、`missing`、`conflict`、`unknown`、`unsupported`。
- 推荐动作；推荐动作只展示，不自动执行。

#### 交付顺序

- M3-A：Java + Maven/Gradle、Node + npm/pnpm/yarn。
- M3-B：Rust + rustup、Python + 项目虚拟环境。
- M3-C：静态资源预览、用户配置的 Nginx、Docker 备选方案。

#### 环境处理原则

- Java 优先项目 Maven/Gradle Wrapper；JDK 路径按项目映射。
- Node 根据 `packageManager`、锁文件、`engines` 和版本文件共同判断，不猜包管理器。
- Rust 优先 `rust-toolchain.toml`，通过明确工具链调用 Cargo。
- Python 优先项目 `.venv`，不模糊回退到任意系统 Python。
- 静态资源必须由用户确认发布目录；开发预览优先轻量内置服务，生产 Nginx 只使用用户明确配置。
- Docker 是可选隔离运行方案，不因为发现 Dockerfile 就默认改用容器。

#### 有意不做

- 不启动项目。
- 不安装缺失环境。
- 不修改系统环境变量。
- 不让 AI 判断最终可执行路径。

#### 验收门槛

- 每个 `ready` 都能追溯到项目证据和本机版本核验。
- 缺失、冲突、无法识别不会显示为可运行。
- Windows 路径、WSL 路径和 macOS/Linux 可执行路径不混用。
- 检测失败不覆盖用户已经保存的有效运行配置。

### M4：单项目受管运行器

#### 前置条件

M3 的环境报告和运行配置格式已经稳定，并通过至少 Java、Node 两类项目的人工验证。

#### 目标

用户确认运行配置后，CodeShelf 可以启动、观察、停止和重启单个项目的长期进程。

#### 范围

- 保存项目级运行配置：可执行文件、参数、工作目录、环境变量、就绪检测。
- 启动前展示完整方案并再次核验可执行文件。
- 流式展示 stdout/stderr，日志采用有上限的环形缓冲。
- 显示启动中、运行中、停止中、已停止、启动失败、异常退出状态。
- 支持端口或 HTTP 就绪检测；检测失败不等同于进程不存在。
- 应用正常退出时清理受管子进程；异常退出后的遗留进程处理需要单独验证。
- 窗口隐藏时不靠前端轮询维持状态，使用事件或受控低频查询。

#### 有意不做

- 不执行用户未确认的 AI 生成命令。
- 不在第一版提供复杂 DAG、并行矩阵和 CI 功能。
- 不把终端里由用户手动启动的进程冒充为受管进程。

#### 验收门槛

- Windows、macOS、Linux 至少各有明确的进程组/进程树回收策略。
- 停止项目后无遗留子进程占用端口。
- 大量日志不会无限增加内存，日志截断有明确提示。
- 启动失败、就绪检查失败和异常退出能被区分。
- 运行器不依赖 AI Provider。

### M5：多项目工作区（开发场景）

#### 前置条件

单项目运行器已经稳定；启动、停止、异常退出和应用关闭回收均通过实机验证。

#### 目标

将多个已经有有效运行配置的项目或基础设施组合为一个可联合启动、观察和停止的开发场景。

#### 首版范围

- 从现有项目/分类中选择场景成员。
- 为成员指定角色和明确的顺序。
- 按顺序启动；前一成员达到就绪状态后才启动下一成员。
- 聚合展示各成员 Git 状态和运行状态。
- 按相反顺序停止。
- 某成员失败时停止后续启动，并保留已启动成员状态供用户决定是否回滚。

#### 有意不做

- 不新增只有名称和成员列表的空壳工作区。
- 不在首版做任意有向图、条件表达式或分布式任务编排。
- 不未经确认自动拉取代码、切换分支或安装依赖。

#### 验收门槛

- 与分类的职责在界面和数据模型上清晰分开。
- 场景删除不删除项目、分类或项目运行配置。
- 单个成员失败不会让界面谎报整个场景已就绪。
- 场景停止后不遗留受管进程。

### M6：可选 AI 增强

#### 前置条件

对应本地能力已经独立完成，且在没有任何 AI 配置时通过验收。

#### 候选增强

- 搜索：根据用户问题建议关键词、文件类型和搜索范围；用户确认后仍由本地引擎执行。
- 搜索：对少量命中片段进行分组、归纳和解释。
- 环境：解释 `missing/conflict/unknown` 报告，生成可复制但不自动执行的修复建议。
- 项目知识：复用现有背景知识能力，生成项目说明、上手指南，并保留证据文件。

#### 强制约束

- AI 按钮为显式二次操作，不成为搜索或运行主按钮。
- 没有 Provider 时不弹阻断错误，不强制跳转配置页。
- 调用前展示将发送的项目、文件和片段范围。
- 默认不发送完整仓库，不发送敏感文件命中。
- AI 输出必须标识模型、生成时间和“AI 生成”。
- AI 输出可以单独删除、重新生成，不影响本地结果。

#### 验收门槛

- 删除所有 AI 配置后，本地功能行为与增强前一致。
- AI 请求失败不会清空或替换本地结果。
- 关闭 AI 后不会产生后台模型调用或 Token 消耗。

### M7：项目知识库 / 自动说明书

#### 现有基础

简历模块已经能在项目根目录边界内分析文件，并按项目保存可编辑的 `background.md`。本阶段不再新造一套项目读取 Agent，而是将“项目知识”从简历专用流程提升为书架的正式领域能力，同时保持原有简历生成兼容。

#### 目标

为每个书架项目维护一份可追溯、可更新、可导出的项目说明书；没有 AI 时仍能生成基础版本，配置 AI 后可在证据范围内生成自然语言说明。

#### 无 AI 基础能力

- 汇总项目名称、路径、分类、标签、远程仓库、默认分支和最近提交。
- 解析主要语言、构建工具、清单文件、运行时版本要求和可用脚本。
- 摘取 README 中已有的简介、安装、运行和部署章节；保留来源位置。
- 生成受忽略规则约束的有限目录结构，而不是保存完整文件树。
- 每项确定性信息显示证据来源和采集时间。
- 记录生成时的 Git HEAD 与关键清单指纹；变化后标记 `stale`，不静默冒充最新。
- 支持用户编辑、恢复自动生成版本、查看历史和导出 Markdown。

#### 可选 AI 增强

- 根据本地基础知识和用户明确允许的证据文件生成项目简介、架构说明和新人上手指南。
- 每个结论尽可能链接到证据文件；证据不足时留空或标记未知。
- AI 内容和确定性字段分区展示，允许单独删除和重新生成。

#### 有意不做

- 不在后台持续扫描所有仓库；首版由用户手动刷新或在明确事件后标记过期。
- 不因为 Git HEAD 变化就自动调用 AI。
- 不从代码中编造业务指标、团队规模、上线效果或未证实架构结论。
- 不复制一份与简历背景知识互不兼容的第二套项目知识存储。

#### 验收门槛

- 没有 AI Provider 时可生成、编辑、保存和导出基础说明书。
- 每个自动字段能追溯到项目元数据、Git、清单或 README 证据。
- 项目更新后能准确显示“可能已过期”，旧内容不会被自动覆盖。
- 简历生成仍能读取既有背景知识，历史内容不丢失。
- 敏感文件规则同时约束索引、读取、搜索和 AI 输入。

### M8：代码备份与镜像中心

#### 现有基础

项目详情已支持多个 Git 远程仓库，并已有从源远程 fetch 后向目标远程同步当前分支或全部分支的能力。本阶段将单项目手动同步提升为书架级备份策略、执行记录和恢复可信度管理。

#### 目标

用户可以为项目指定主远程和一个或多个备份目标，集中查看哪些仓库已备份、哪些备份落后、哪些备份失败，并在明确确认后执行镜像同步。

#### 首版范围

- 为单个或批量项目配置源远程、目标远程、分支范围和是否包含标签。
- 支持 GitHub/Gitee/GitLab 等普通远程，也允许 Git 能识别的本地或 NAS 裸仓库路径。
- 提供手动“立即备份”；首版不默认定时执行。
- 记录开始时间、结束时间、源 HEAD、目标、成功/部分失败/失败以及逐分支结果。
- 同步后重新读取目标 refs，验证预期分支和标签确实存在。
- 书架集中显示最后成功时间、最后验证时间和失败原因。
- 明确提示：Git 远程备份不包含未提交、未跟踪和被忽略文件。

#### 后续增强

- 在用户明确开启后，利用现有调度能力执行定时备份。
- 应用启动或项目提交后只标记“需要备份”，不立即静默推送。
- 备份失败通过现有通知中心提示，并允许从失败项重试。

#### 有意不做

- 不默认 force push，不把备份失败自动升级为强制覆盖。
- 不自动创建第三方平台仓库或管理平台账号权限。
- 不把 Git 镜像宣传为工作区未提交内容或本地环境的完整备份。
- 不在首版后台持续 fetch 全部项目。

#### 验收门槛

- 一个项目失败不阻断其他项目，批量结果按真实成败对账。
- “命令返回成功”和“目标 refs 验证通过”分开记录。
- 凭证继续由系统 Git 凭证链处理，CodeShelf 不新增明文凭证存储。
- 断网、认证失败、目标只读、部分分支失败均有可恢复状态。
- 没有 AI Provider 时全部功能可用，备份过程不调用 AI。

### M9：冷藏书架 / 项目归档

#### 目标

为长期不用的项目提供“从主书架隐藏但保留信息”的逻辑归档，以及可选的磁盘冷藏与验证恢复流程，填补“继续占据主书架”和“直接删除”之间的空白。

#### M9-A：逻辑归档

- 项目文件保持原位，只增加归档状态、归档时间和原因。
- 主书架默认不显示归档项目，提供独立冷藏书架入口。
- 保留分类、标签、远程、知识、运行配置和备份记录。
- 恢复只改变状态，不触碰项目目录。

#### M9-B：磁盘冷藏

- 冷藏前执行路径、权限、磁盘空间、Git 状态和备份状态检查。
- 用户选择是否包含未跟踪/被忽略文件，并在执行前展示范围和估算大小。
- 先写入目标目录中的临时产物，完成校验后再原子切换为正式归档。
- 保存归档格式版本、校验和、原路径、项目元数据、Git HEAD、远程和内容范围。
- 默认“生成并验证归档但保留源目录”；删除源目录必须单独二次确认。
- 恢复前检查目标路径冲突和可用空间；先恢复到临时目录，校验成功后再入库。

#### 有意不做

- 不在工作区存在未提交修改时默认删除源目录。
- 不把“有远程仓库”直接等同于所有本地内容已备份。
- 不在首版提供跨机器云同步服务。
- 不复用当前“删除项目目录”操作假装完成归档；归档必须可验证恢复。

#### 验收门槛

- 逻辑归档和磁盘冷藏是两个明确动作，用户不会误删文件。
- 归档中断、磁盘写满或校验失败时，源目录保持不变。
- 删除源目录前已经存在通过校验的正式归档，并明确展示可恢复位置。
- 恢复后文件校验通过，项目元数据、Git 状态和书架引用一致。
- 非 Git 项目、无远程项目和含未跟踪文件项目均有明确处理路径。

### M10：从现有项目创建新项目

#### 目标

允许用户选择书架中的成熟项目作为来源，通过可预览的复制与变量替换流程创建一个新项目，并可选择初始化 Git、配置远程和自动加入书架。

#### 首版范围

- 选择源项目、目标父目录和新项目名称。
- 默认遵循源项目 `.gitignore`，排除 `.git`、构建产物、依赖目录和敏感文件。
- 提供“保留 Git 历史”和“移除历史并初始化新仓库”两种明确模式；默认移除历史。
- 支持用户显式配置的文本变量替换，例如项目名、包名、端口和描述。
- 执行前展示文件范围、排除项、变量命中数量、目标路径和后续 Git 动作。
- 先复制到目标父目录下的临时目录；全部步骤成功后再改为最终项目名并加入书架。
- 创建成功后允许继承或重新选择分类、标签、编辑器和运行环境配置。

#### 后续增强

- 将一组经过确认的排除规则和变量规则保存为个人项目模板。
- 为 Java 包名、Node package name、Rust crate name 等提供确定性校验器。
- 可选运行用户明确配置的初始化任务，但必须在独立 Spec 中设计授权、日志和失败回滚。

#### 有意不做

- 首版不运行来源仓库中携带的任意初始化脚本或 post-create hook。
- 不用 AI 猜测并批量修改所有业务名称、数据库名或领域概念。
- 不复制 API key、`.env`、证书、私钥和其他命中敏感规则的文件。
- 不覆盖已经存在的目标目录。

#### 验收门槛

- 目标路径已存在、空间不足、复制失败或替换失败时，不留下被误认为成功的新项目。
- 源项目在整个过程中只读，不修改原文件和 Git 状态。
- 敏感文件默认排除且可解释；用户不能在无提示情况下复制密钥。
- 变量替换只作用于确认过的文本文件，二进制文件保持原样。
- 成功后新项目路径唯一、Git 模式符合选择，并能从书架正常打开。

## 数据模型方向

以下是跨阶段的概念模型，用于保持边界一致；不是最终 SQL，也不要求提前建表。

### 本地搜索

```text
ProjectSearchRequest
  - searchId
  - projectIds
  - mode: text | regex | filename | dependency
  - query
  - fileGlobs
  - includeUntracked
  - limits

ProjectSearchMatch
  - projectId
  - relativePath
  - line / column
  - preview
  - source: git_tracked | filesystem | manifest
```

M1 不要求存储迁移；只在确认需要保存历史、收藏查询或增量元数据缓存时再设计表结构。

### 环境检测与运行

```text
RuntimeDetectionReport
  - projectId
  - evidence[]
  - requirements[]
  - localCandidates[]
  - status

ProjectRunProfile
  - projectId
  - executable
  - args[]
  - workingDirectory
  - environment
  - readyCheck
  - userConfirmedAt
```

检测报告可以临时生成；用户确认的运行配置需要持久化。进入 M4 前必须单独设计 SQLite migration 与兼容策略。

### 开发场景

```text
DevelopmentScene
  - id / name
  - members[]

SceneMember
  - projectId 或基础设施引用
  - role
  - runProfileId
  - order
```

进入 M5 前再确定场景与分类的关系表，不提前为“可能需要”建表。

### 项目知识

```text
ProjectKnowledgeDocument
  - projectId
  - deterministicFacts[]
  - markdownContent
  - evidenceRefs[]
  - sourceHead / sourceFingerprint
  - state: fresh | stale | generating | failed
  - userEdited
  - updatedAt
```

优先评估如何复用现有 `background.md` 和历史记录，避免书架知识与简历知识分叉。确定性字段和 AI 生成正文需要保留边界。

### 备份与镜像

```text
MirrorPolicy
  - projectId
  - sourceRemote
  - targetRemotes[]
  - branchScope
  - includeTags
  - schedule: manual | explicit_schedule

MirrorRun
  - policyId
  - sourceHead
  - startedAt / finishedAt
  - status
  - branchResults[]
  - verificationResult
```

策略与执行历史属于结构化核心数据，进入 M8 前设计 SQLite migration。不得把凭证写入策略表。

### 项目归档

```text
ProjectArchiveRecord
  - projectId
  - mode: logical | disk
  - archivePath
  - originalPath
  - contentScope
  - sourceHead
  - checksum
  - formatVersion
  - status
  - createdAt / verifiedAt / restoredAt
```

逻辑归档状态属于项目生命周期；磁盘归档记录必须保存内容范围与校验信息，不能只有一个压缩包路径。

### 从现有项目创建

```text
ProjectTemplateRecipe
  - sourceProjectId
  - name
  - excludes[]
  - variables[]
  - gitMode

ProjectCreationRun
  - recipeId
  - sourcePath / targetPath
  - previewSummary
  - status
  - createdProjectId
```

首版可以只保存最近一次创建配置；只有确认用户会重复使用后才把 Recipe 提升为长期模板数据。

### AI 增强

```text
AiEnhancement
  - feature
  - localResultFingerprint
  - provider / model
  - generatedAt
  - content
```

AI 内容不得塞回搜索命中、检测证据或运行配置的确定性字段。

## 安全、隐私与资源约束

### 文件边界

- 只搜索书架中明确登记且当前存在的项目目录。
- 所有路径 canonicalize 后校验仍位于对应项目根目录。
- 符号链接越界、路径失效、权限不足分别返回明确状态。
- M1 纯本地搜索遵循明确的文件范围、生成目录排除和 `.gitignore`，结果只存内存，不发网络。
- 现有敏感规则当前服务于背景知识生成且包含正常代码目录，不直接套用到 M1；AI 增强读取本地结果时必须在出站边界重新过滤并展示发送预览。

### 命令与进程

- 运行配置使用明确可执行文件、参数数组和工作目录，避免用字符串拼接任意 Shell。
- 所有长期进程必须由受管进程服务登记，不能只保存 PID 后不核验身份。
- 停止、超时、应用退出必须处理子进程树。
- 日志、事件队列、搜索结果和 AI 上下文均有硬上限。

### AI 数据

- 默认只发送搜索命中或检测报告，不发送全仓库。
- 用户可查看本次将发送的片段和文件列表。
- 敏感规则拦截不能被提示词或模型请求绕过。
- AI 生成的命令、环境变量或配置必须经过用户确认，且不得直接进入运行器。

## 影响面总览

本路线图预期会影响以下模块，但每阶段只改其实际需要的部分：

- 前端：书架页、项目详情、设置，以及后续搜索、知识、运行、备份、归档和创建向导页面
- 状态：`projectsStore`、`settingsStore`，必要时新增聚焦单一领域的 Store
- Rust：项目搜索、清单解析、环境检测、受管进程、开发场景、镜像、归档、复制与校验命令
- Node sidecar：M7 评估复用现有项目知识读取和生成流程，避免书架与简历重复实现
- 存储：M4/M5/M7/M8/M9 预计需要 SQLite migration 或现有知识存储兼容设计；M1/M2/M3 应尽量先无迁移交付
- AI：复用现有 Provider 和敏感文件配置，但保持对本地模块的单向可选依赖

跨阶段约束：

- 改 Tauri 命令签名后运行 `cargo test --lib export_bindings`，不手改 `src/bindings.ts`。
- Windows 专有进程代码必须走 Docker 交叉编译验证。
- 后台轮询必须有 `document.hidden` 守卫；能用事件就不增加轮询。
- 项目关系、运行配置等结构化核心状态必须经过 SQLite migration；纯 UI 偏好继续沿用现有设置存储，不另建随意状态文件。

## 验证矩阵

| 阶段 | 必验场景 | 预期结果 |
|---|---|---|
| M1 | 未配置任何 AI | 搜索全部核心功能可用，无模型请求 |
| M1 | 50 个项目、部分路径失效 | 正常项目继续返回；失败项目单独标记 |
| M1 | 搜索取消、结果超限 | 后台及时停止；明确显示取消或截断 |
| M2 | 清单缺失/语法错误/动态版本 | 分别显示未发现、解析失败或未知，不冒充确定版本 |
| M3 | JDK/Node 多版本并存 | 展示候选和证据，不擅自改全局默认版本 |
| M3 | 环境缺失 | 显示缺失与修复建议，不自动安装 |
| M4 | 长期服务持续输出日志 | 内存有界；日志截断可见；进程仍可停止 |
| M4 | 应用退出/进程异常退出 | 状态准确，受管子进程按策略回收 |
| M5 | 中间成员启动失败 | 后续不启动；已启动成员状态清晰 |
| M6 | AI 超时/删除 Provider | 本地结果保持，功能不被阻断 |

| M10 | 目标已存在/复制失败 | 不覆盖目标，不产生伪成功项目记录 |
| M10 | 源项目含敏感文件 | 默认排除并在预览中明确说明 |
| 全阶段 | 中文、空格、Windows/WSL 路径 | 路径解析不越界、不误判 |

每阶段代码验证按实际影响执行：

- 前端：`npx tsc --noEmit`
- Rust：`cd src-tauri && cargo check`
- Rust 非平凡逻辑：`cd src-tauri && cargo test --lib`
- Tauri 命令签名：`cd src-tauri && cargo test --lib export_bindings`
- Windows 专有逻辑：Docker 交叉编译
- 涉及 sidecar 或构建依赖：`npm run build`
