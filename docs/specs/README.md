# Specs（需求层 / 架构层）

存放**大改动**的规格说明。写 Spec 的目的是让改动有唯一真相源，而不是补文档。

## 什么时候写

只有这四类需要：**新增工具箱工具**、**跨模块重构**、**数据结构/存储迁移**、**外部协议变更**（MCP、sidecar RPC）。

日常 bugfix、UI 微调、依赖升级**不写**。判断标准与理由见 [AI-CODING.md](../AI-CODING.md#什么时候写-spec)。

## 命名

`YYYYMMDD-NN-简述.md`，例如 `20260728-01-工具箱新增端口转发.md`。

## 模板

```markdown
# <标题>

## 背景
要解决的问题是什么、为什么现在做。

## 目标
- 可验收的目标，一条一件事

## Non-Goals
- 明确**不做**什么（这一节最重要，不写 AI 一定会自由发挥）

## 方案
模块划分、接口约定、数据流。写 **WHAT 不写 HOW** —— 不要贴完整伪代码。

## 影响面
- 涉及文件/模块：
- 是否涉及 Windows 专有代码：是 → 必须交叉编译验证
- 是否涉及数据文件读写：是 → 必须走 write_atomic / parse_json_or_backup
- 是否改动 Tauri 命令签名：是 → 必须重新生成 bindings

## 验证方式
怎么证明它真的生效了：跑什么命令、点哪些操作、看什么结果。
```

## 抽象度自检

写完问自己：**"换一个技术栈实现，这份 Spec 是否依然有效？"**
答案为否，说明混入了 HOW（实现细节、伪代码），需要上提抽象度。Spec 膨胀会打满上下文，反而拖累。
