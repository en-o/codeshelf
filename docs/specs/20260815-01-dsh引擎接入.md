# 把 DeepSeek Harness（dsh）接成 Chat 的后端引擎

> 上游：https://github.com/deepseek-ai/deepseek-harness （MIT，developer preview）

## 背景

CodeShelf 的 Chat 现在自己跑 agent 循环：前端 `useChatRunner.ts` 组消息 → `chat_stream`
→ 收 tool_calls → 弹审批 → 执行 Rust 工具 → 回灌下一轮。dsh 本身就是一个完整的
agent harness（自带 agent loop、工具集、沙箱、会话持久化、上下文压缩、subagent）。

接进来之后的分工：**dsh 跑 agent，CodeShelf 管界面与会话归档**。两套引擎在**会话级别并存**
（`ChatSession.engine`），老会话不受影响。

## 目标

- 应用内托管安装固定版本的 dsh，用户不用自己折腾 npm
- Chat 会话可切到 dsh 引擎，流式正文、工具调用、待办都渲染进现有 UI
- 模型复用现有 AI 供应商配置，不让用户配第二遍密钥

## Non-Goals

- ❌ 不替换现有内置引擎，也不迁移历史会话
- ❌ 不把 dsh 或 Node 22 打进安装包（依赖树很大，且 dsh 每次升级都要重发 CodeShelf）
- ❌ 不实现 dsh 的 Web UI / ACP / Python SDK 那几条路
- ❌ 不给 dsh 会话接 CodeShelf 自己的工具与 MCP —— dsh 有自己的一套，混用只会两边都不对

## 接口（实测，非文档推断）

dsh 的 SDK 运行时通过 **stdio 上的换行分隔 JSON-RPC 2.0** 提供服务，
由 `@deepseek-ai/dsh-sdk-jsonrpc-server` 插件实现。

| 方向 | 方法 | 载荷 |
|---|---|---|
| C→S | `initialize` | `{ cwd, provider, model, maxTokens? }` → `{ serverInfo }` |
| C→S | `session/prompt` | `{ sessionId, contentBlocks }` → `{ messageId }`（只是入队回执） |
| C→S | `shutdown` | `{}` → `{}`，服务端随后自行退出 |
| S→C | `session.event` | `{ sessionId, event }`，完整会话日志事件 |
| S→C | `session.status` | `{ sessionId, status: running \| idle }` |
| S→C | `subagent.started` / `subagent.finished` | 子 agent 生命周期 |

用到的事件类型：`assistant/chunk`（text-delta / reasoning-delta）、`assistant/message`
（定稿，含 usage）、`tool/call`、`tool/result`、`todo/write`、`turn/start` `turn/end`
（`reason.kind === 'error'` 即失败）、`user/message`。

**stdout 就是协议**：dsh 侧不能挂任何 stdout logger，诊断信息全在 stderr。

## profile 组成

dsh 的 profile = `$DSH_HOME/profiles/<名字>/` 下的 `package.json` + `cordis.patch.yml`。
CodeShelf 生成的这一份（`src-tauri/src/commands/dsh/runtime.rs` 里的常量）有三处**必须**的改动：

| 改动 | 不改会怎样 |
|---|---|
| `hmr: disabled` | dsh-base 默认挂 HMR，它要求 node 带 `--expose-internals`；不关就是「启动即失败」 |
| `approval.policy: never` | 协议里服务端**不会**向客户端发请求（官方标注 server→client requests 是 dead capability），审批问题递不出来，保持默认 `ask` 会让对话卡死 |
| `permission.presets.*.approval: never` | permission-presets 校验「组合出的 sandbox+approval 必须命中某个预设」，只改 approval 会报 `composed sandbox and approval defaults match no preset` |

沙箱模式仍是 `workspace-write`（由 `DSH_PERMISSION_MODE` 决定，默认即此），文件写入被限制在会话工作目录内。

profile 依赖用 `npm install --legacy-peer-deps` 装：默认行为会把 peer（dsh-agent /
dsh-llm / dsh-session …）在 profile 里再装一份，与 dsh 本体的副本重复，多出二十几个包；
实测只装 `dsh-sdk-jsonrpc-server` + `dsh-sdk-protocol` 就能正常加载。

## 硬约束

- **Node ≥ 22**。dsh 用到 `Promise.withResolvers` 与 `zlib.createZstdDecompress`，
  Node 20 上插件树直接加载失败。仓库内置的 sidecar node（跟随构建机版本，当前 v20）**不能复用**，
  找的是用户机器上的 node（PATH + nvm 目录扫描，复用 `claude_code::get_extra_path_dirs`）。
- **版本 pin 死**在 `DSH_VERSION`（当前 `0.1.0-rc.6`）。上游明说 developer preview 会有
  破坏性变更，跟 `latest` 等于让用户在毫无察觉时换协议。改这个常量必须重跑下面的冒烟。

## 已知限制（要在 UI 上讲清楚）

- **没有中途取消**：协议没有 cancel 方法，官方给的唯一手段就是关掉进程。停止 = 重启引擎。
- **会话 id 一次性**：同一个 `sessionId` 在下一个运行时里再用会报
  `already has a persisted log on disk that does not match this live session`。
  所以每次启动引擎都要为会话生成新的 dsh sessionId —— **重启引擎后 dsh 侧是新上下文**，
  CodeShelf 这边的完整记录仍在。
- **审批弹窗对 dsh 会话不生效**：权限由 dsh 的沙箱模式决定，不是 CodeShelf 的工具授权。
- **Windows**：dsh 的持久 PTY 组合不支持 Windows，本期只保证启动 + 对话 + 文件工具。

## 落地拆分

1. **运行时探测与托管安装**（本次）：`commands/dsh/runtime.rs`、设置页 `DshSettings.tsx`。
2. **引擎进程与事件桥**：`commands/dsh/engine.rs`，常驻子进程 + JSON-RPC + Tauri 事件。
3. **Chat 接入**：`ChatSession.engine`、`useDshRunner`、会话配置里的引擎选择。

## 验证

```bash
cd src-tauri && cargo test --lib dsh && cargo test --lib export_bindings
npx tsc --noEmit
```

不花钱的协议冒烟（把 `DEEPSEEK_BASE_URL` 指到一个不通的地址）：
`initialize` 应返回 `serverInfo`，`session/prompt` 应返回 `messageId`，
最后 `turn/end` 带 `TRANSPORT` 错误、`session.status` 回到 `idle`。
这条路径覆盖除真实模型调用外的全部接线。

真机：设置 → dsh 引擎 → 一键安装 → 状态变「已就绪」；新建会话选 dsh 引擎 + 工作目录 → 发一句话。
